# Tripothon 한눈에 이해하기

게임 개발 계획 · 캐릭터 제작의 변화 · 클라이언트–서버–DB 연결

**기준일: 2026년 10월 4일 · 처음 프로젝트를 접하는 사람을 위한 안내서**

이 안내서는 저장소의 코드, 제작 기록, 사용자 결정 사항을 합쳐 설명합니다. 과거 실험을 모두 현재 제품의 기능으로 취급하지 않습니다. 개발 기준본은 0.9.2이며, 최신 멀티플레이 테스트본과 새 캐릭터 제작 계획은 별도로 진행 중입니다.

## 1. 3분 만에 이해하는 우리 게임

**Tripothon — 일곱 밤, 나의 마을**은 마을에서 생활하고, 생존 도전을 통해 보상을 얻고, AI로 만든 가구로 자기 공간을 꾸미는 게임입니다.

```text
마을 생활                   7일 생존 도전
농사 · 낚시 · NPC 교류  ──→  탐험 · 채집 · 전투 · 생존
       ↑                           │
       │                           ↓
나만의 공간 꾸미기          성과 보상 ‘별씨’
색칠 · 배치 · 가구 사용 ←── AI 공방에서 가구 제작
```

현재 데모의 ‘7일’은 **게임 속 시간**입니다. 한 차례 도전은 약 420초, 실제 시간으로 약 7분을 기준으로 구성되어 있습니다. 향후 콘텐츠와 밸런스에 따라 조정할 수 있습니다.

플레이어는 Godot로 만든 게임을 실행합니다. 게임 화면과 입력은 플레이어 PC가 처리하고, 계정·보상·소유권·중요한 게임 규칙은 서버가 관리합니다. 저장 데이터는 서버의 DB에, 생성한 3D 파일은 별도의 파일 저장소에 보관합니다.

개발 중인 캐릭터는 **Explorer B**입니다. 캐릭터 디자인과 Godot 엔진은 유지합니다. 사용자가 바로잡은 제작 방향은 **얼굴을 포함한 모델을 Tripo로 생성 → Blender에서 형태·토폴로지 정리 → 애드온으로 페이스 리깅**입니다. MPFB 템플릿으로 캐릭터 모델을 대체하는 방식은 채택하지 않습니다.

### 이 문서에서 사용하는 상태 표시

| 표시 | 의미 |
|---|---|
| **기준본** | 다시 실행하고 비교할 수 있도록 저장한 개발 결과. 출시 완료라는 뜻은 아닙니다. |
| **로컬 검증** | 개발 PC 또는 로컬 테스트 환경에서 작동 기록이 있음. 외부 사용자 환경까지 검증한 것은 아닙니다. |
| **실험** | 별도 모델·장면·도구에서 시험한 결과. 본 게임 반영 여부는 별도입니다. |
| **선택·대기** | 채택하기로 한 방향. 설치·제작·검증을 아직 마치지 않았습니다. |
| **향후** | 앞으로 수행할 작업 또는 검토 후보입니다. |

## 2. 지금 어디까지 왔나

| 영역 | 현재 확인된 상태 | 남은 일 |
|---|---|---|
| 게임 실행 기준 | **기준본 0.9.2.** 조작·카메라·공간 크기 정리. 기존 Explorer B hand-v4 사용 | 이후 기능과 아트를 합친 통합 기준본 만들기 |
| 마을 생활 | 농사·낚시·상점·창고·NPC 등 기본 기능 구현 | 화면 품질, 행동, 상호작용, 재미 다듬기 |
| 생존 도전 | 서버가 관리하는 도전·전투·보상 흐름 구현 및 검증 기록 | 한 맵의 완성도, 난이도와 반복 플레이 조정 |
| AI 가구 공방 | 계획·견적·생성·소유·색칠·배치 흐름의 **로컬 검증** 기록 | 온라인 운영 정책과 유료 생성 공개 범위 확정 |
| 온라인 데모 | HTTPS 서버 가동. 이번 정리 때 `/health` 응답 확인 | 전체 플레이의 최신 통합 검증은 별도 필요 |
| 멀티플레이 | **최대 3인 마을 방문 / 2–3인 협동 생존을 로컬 검증** | 최신 서버 배포, 서로 다른 집·네트워크에서 검증 |
| 거래 | 매물·거래 관련 **백엔드 구현 있음**. 플레이어 거래 UI는 숨김·후순위 | 거래 규칙, UI, 운영 검증 후 공개 |
| 캐릭터 얼굴 | 여러 수작업 보정 버전을 보존. 사용자가 품질 한계를 확인 | 새 표준 얼굴 기반 방식으로 작은 시제품부터 검증 |
| 새 캐릭터 도구 구성 | **MPFB 2.0.17·Rigify 설치 및 템플릿 기능 시험 완료.** 제작 모델은 Tripo 사용 | 다듬은 Tripo 얼굴에 실제 페이스 리깅 적용·검증, 음성 립싱크, Godot 내보내기 |

**온라인과 로컬은 같은 상태가 아닙니다.** 이번에 확인한 원격 `/health`는 `mode=live`, `protocol=6`, `studio_tripo_enabled=false`를 반환했습니다. 멀티플레이 버전 필드는 응답에 표시되지 않았습니다. 따라서 온라인 데모에서 최신 협동 기능이나 유료 Tripo 생성을 바로 쓸 수 있다고 안내하면 안 됩니다.

기존 상세 문서의 “멀티플레이 미구현”과 오래된 캐릭터 우선순위는 작성 당시의 기록입니다. 최신 멀티플레이 상태는 [멀티플레이 개발 기록](C:/lsm26/triphthonS1/docs/MULTIPLAYER_20261004.md), 캐릭터 방향은 [새 제작 파이프라인 명세](C:/lsm26/triphthonS1/art/characters/explorer_b_pipeline_v3/pipeline.json)를 우선합니다.

## 3. 전체 개발 계획: 큰 방향과 실제 단계

### 큰 방향은 다섯 가지입니다

1. **게임의 중심을 완성합니다.** 맵·캐릭터·마을 생활·7일 생존의 기본 재미를 만듭니다.
2. **Tripo를 게임 경험에 연결합니다.** 보상으로 가구를 만들고 실제로 배치·사용하게 합니다.
3. **거래를 추가합니다.** 생성물의 소유권과 거래 규칙을 확정하고 플레이어 UI를 엽니다.
4. **서버·DB 운영을 강화합니다.** 사용량에 맞춰 저장·처리·복구 구조를 확장합니다.
5. **콘텐츠를 늘립니다.** 지역, NPC, 가구, 이야기와 활동을 확장합니다.

계정 인증과 소유권 확인 같은 기본 서버 책임은 이미 필요하므로 4번까지 미루는 항목이 아닙니다. 이 순서는 제품 우선순위이고, 보안·저장·멀티플레이 작업은 여러 단계에 걸쳐 진행됩니다.

### 기존 8단계 실행 계획을 현재 상태에 맞춰 읽기

| 단계 | 목표 | 현재 위치 | 다음 단계로 넘어갈 기준 |
|---|---|---|---|
| **1. 기준본 확보** | 현재 게임을 검증하고 재현 가능한 상태로 보관 | 0.9.1 기록 확보 | 실행 방법과 파일이 남아 있고 회귀 비교 가능 |
| **2. 조작·카메라·비율** | 걷기·달리기·시점·캐릭터와 공간 크기 정리 | 0.9.2 기준 확보 | 이동과 상호작용이 일관되고 시점이 안정적 |
| **3. 마을 한 구역 완성** | 목표 품질을 보여주는 마을·캐릭터 기준 장면 완성 | 별도 아트 실험 진행. 캐릭터 제작 방식 재정립 중 | 본 게임 안에서 캐릭터·건물·조명·재질이 함께 승인됨 |
| **4. UI·상호작용 정리** | 처음 하는 사람도 생활·공방·배치를 이해 | 기반 기능 있음, 정돈 필요 | 안내 없이도 핵심 행동을 수행하고 오류에서 회복 가능 |
| **5. NPC·마을 생활 강화** | 농사·낚시·대화가 하나의 생활 흐름으로 연결 | 기능과 해루 캐릭터·동작 등 제작 기록 있음 | NPC 반응과 생활 활동이 자연스럽게 이어짐 |
| **6. 생존 맵 하나 완성** | 7일 도전의 시작부터 종료까지 재미와 균형 확보 | 생존·보상 구현, 협동 기능 로컬 검증 | 솔로·협동에서 진행 중단, 보상 중복, 불합리한 전투 없이 완주 |
| **7. 보상→생성→꾸미기 완성** | 별씨 사용이 실제 공간 변화로 이어짐 | 로컬 통합 검증. 공개 서버의 유료 생성은 꺼짐 | 견적·확인·실패 처리·소유·재접속까지 연결됨 |
| **8. 확장·운영** | 콘텐츠 확대, 서버 운영, 거래 공개 준비 | 후속 단계 | 외부 환경 검증, 백업 복원, 비용·용량 기준을 갖추고 확장 |

단계 번호는 작업을 설명하기 위한 기준입니다. 현재는 **3단계의 캐릭터 품질 개선과, 6–8단계에 걸친 멀티플레이·운영 작업이 병행되는 상태**입니다. 모든 팀 작업이 한 단계에만 머물러 있는 것은 아닙니다.

지역 콘텐츠에는 숲·채석장·서리 지역의 챕터 구조가 있습니다. 지역의 존재와 목표 수준의 아트·밸런스 완성은 구분해서 판단합니다.

## 4. ‘AI 생성’은 서로 다른 두 과정입니다

| 구분 | 개발자가 캐릭터·공용 아트를 제작 | 플레이어가 게임 안에서 가구를 제작 |
|---|---|---|
| 사용 목적 | 주인공, NPC, 의상, 머리카락, 공용 배경 제작 | 개인 공간에 놓을 새 가구 제작 |
| 사용자 | 개발자·아티스트 | 게임 플레이어 |
| 주요 도구 | 참조 이미지, Tripo, Blender, 리깅·애니메이션 도구 | Godot 공방 UI, FastAPI 작업 처리, LLM, Tripo |
| 검수 | 이미지 승인 → 모델·변형·동작 검토 | 서버 입력·계획·비용·파일 검증, 플레이어 확인 |
| 저장 | 편집 원본 `.blend` → 배포용 `.glb` → `game/assets` | 서버의 생성물 파일 + DB의 소유권·상태 |
| Blender 사용 | 사용 | **플레이어 런타임 경로에는 사용하지 않음** |
| 현재 핵심 과제 | 얼굴 품질과 안정된 표정 구조 | 생성 비용·권한·작업 상태·게임 내 배치의 일관성 |

```text
개발용 아트 제작
참조 승인 → Tripo / 표준 메시 → Blender 편집·리깅 → GLB → Godot 공용 자산

플레이 중 가구 생성
공방 입력 → 서버 계획·견적 → 플레이어 확인 → 생성 API → 개인 자산 → 배치
```

캐릭터 제작에 쓰는 P2/HD 선택이 게임 공방의 모든 생성 설정을 자동으로 바꾸는 것은 아닙니다. 두 과정은 설정·비용·검증 기록을 따로 관리합니다.

## 5. 캐릭터 생성 파이프라인: 무엇을 시도했고 왜 바꾸나

아래 A–F는 설명을 위해 붙인 이름입니다. 저장소의 모든 폴더가 이 버전 체계를 사용하는 것은 아닙니다. 특히 과거 `face_rig_manual_v3`와 새 `explorer_b_pipeline_v3`는 다른 작업입니다.

| 흐름 | 제작 방법 | 얻은 결과와 한계 | 현재 용도 / 주요 기록 |
|---|---|---|---|
| **A. 통째 생성 → 몸 리깅** | 이미지 기반 전체 캐릭터 → 뼈대·기본 동작 → 게임 반영 | 빠르게 움직이는 캐릭터 확보. 정밀 얼굴 제작은 별도 과제 | 게임 기준 캐릭터 **Explorer B hand-v4**. 공용 결과는 `game/assets` |

| **E. P2 흉상 + 머리카락 + 수작업 얼굴** | 목–쇄골까지 얼굴 흉상, 별도 머리카락. 내부 돌출·뒷머리 보완 후 눈·입·턱·표정을 반복 수정 | 프로토타입 확보. 눈 주변 틈·주름, 속눈썹 추종, 입·턱 형태, 동작 연결 문제가 반복되어 주 제작 경로 중단 | `explorer_b_faceit_comparison_p2_v1`, `explorer_b_face_rig_manual_v1`, `v2`–`v2i` 등 보존 |
| **F. MPFB 템플릿 시험** | 무료 애드온 설치와 표정 시험, MPFB 쇄골 흉상 제작 | 도구 기능 시험 기록. 모델링까지 애드온으로 바꾼 것은 사용자 의도와 달라 제작 경로로 채택하지 않음 | **별도 테스트로 보존.** 게임 캐릭터 기준본 아님 |
| **G. Tripo 모델 + 다듬기 + 애드온 페이스 리깅** | Tripo에서 얼굴·신체·부품 생성. Blender에서 외형과 변형용 토폴로지를 정리한 뒤 애드온으로 얼굴 리깅 | 생성 모델의 디자인을 유지하면서 리깅 도구를 활용. 실제 Tripo 얼굴에 맞춘 뼈 배치·웨이트·변형 검증 필요 | **사용자가 확정한 현재 방향.** `explorer_b_pipeline_v3/pipeline.json` |

**Faceit 비교는 아직 ‘구매 전’ 상태입니다.** Faceit을 사용한 성공 결과가 이미 있다는 뜻이 아닙니다. 새 무료 도구 중심 파이프라인에서도 기존 디자인을 유지하며, 게임 엔진을 Unity나 Unreal로 바꾸기로 한 것은 아닙니다.

### 지금까지의 실패에서 유지할 원칙

- **이미지를 먼저 사용자가 검토합니다.** 승인된 참조를 기준으로 유료 3D 생성을 진행합니다.
- **생성된 쿼드와 얼굴 애니메이션용 구조는 다릅니다.** 눈·입 주위의 흐름, 두께, 연결과 변형을 직접 확인합니다.
- **얼굴의 기본형을 확정한 다음 표정을 늘립니다.** 눈·입의 기본 구조가 계속 바뀌면 이미 만든 애니메이션도 다시 손봐야 합니다.
- **원본은 보존하고 승인 결과를 별도 저장합니다.** 최신 파일이라는 이유만으로 게임 기준본을 교체하지 않습니다.
- **수치 검사와 눈으로 보는 검수를 함께 사용합니다.** 충돌 검사를 통과해도 자연스럽거나 보기 좋은 얼굴이라는 증거가 되지는 않습니다.

## 6. 새 캐릭터 제작 방식의 구체적인 순서

**현재 역할 구분:** 모델 제작은 Tripo, 형태·토폴로지 정리는 Blender, 페이스 리깅은 애드온입니다. MPFB·Rigify 설치와 템플릿 시험은 완료했지만, 이는 Tripo 얼굴에 리깅이 완료되었다는 뜻이 아닙니다. [설치·시험 기록](C:/lsm26/triphthonS1/docs/FREE_FACE_ADDONS_TEST_20261004.md)은 도구 테스트로 보존합니다.

### 사용할 도구와 역할

| 도구 | 맡길 일 | 현재 상태와 주의할 경계 |
|---|---|---|
| **MPFB + 공식 사람·표정 자산** | 설치·기능 시험용으로 보존 | 캐릭터 모델 제작에는 사용하지 않음. 템플릿 표정 시험을 Tripo 얼굴의 자동 리깅 성공으로 간주하지 않음 |
| **Rigify / 페이스 리깅 애드온** | 다듬은 Tripo 얼굴의 뼈·조작 컨트롤·변형 설정 | 무료 경로의 우선 후보는 설치된 Rigify. 실제 Tripo 얼굴에 맞춘 뼈 배치·웨이트·눈꺼풀·입 변형 검증은 별도 진행. Faceit은 구매 후 별도 비교 |
| **Blender 기본 기능** | Tripo 모델의 형태 수정, 리토폴로지, 눈·입 내부 정리, 웨이트·보정 표정 작업 | 외형을 먼저 확정한 다음 리깅. 같은 부위를 뼈와 셰이프 키가 중복 변형하지 않게 설정 |
| **Tripo API — P2 / HD** | 얼굴·쇄골 흉상·신체·머리카락·의상·신발·장식의 원본 모델 생성 | 사용자 승인 참조로 생성. 생성 쿼드는 얼굴 변형용 토폴로지 검사가 필요하며, 자동 몸 리깅을 정밀 얼굴 리깅으로 간주하지 않음 |
| **Rhubarb Lip Sync** | 음성에서 시간별 입 모양 신호 추출 | 먼저 검토할 립싱크 후보. 실제 3D 입 모양과 연결해야 하며, 한국어 샘플 검증 필요 |

MPFB 명세에서 선택한 공식 시스템 자산·Faceunits 01·Visemes 팩은 CC0 자산으로 기록되어 있습니다. 애드온 코드의 라이선스와 자산의 라이선스는 별개이며, 다른 외부 팩도 모두 같은 조건이라고 가정하지 않습니다. FaceBuilder는 유료 도구·체험판이므로 무료 핵심 구성에 넣지 않았습니다.

### 작업과 검토 순서

1. **호환 도구 설치와 버전 고정 — 완료.** Blender 4.5.3의 별도 제작 프로필에 MPFB 2.0.17·Rigify 0.6.10과 공식 필수 자산을 준비했습니다. 기존 Blender 파일은 보존했습니다.
2. **승인 이미지로 Tripo 모델 생성.** 얼굴은 머리–목–쇄골 흉상으로 만듭니다. 기존 디자인을 유지하고 새 참조 이미지는 사용자 검토 후 생성에 사용합니다. MPFB 템플릿으로 대체하지 않습니다.
3. **Blender에서 다듬기·리토폴로지.** 외형, 입을 다문 기본형, 눈꺼풀·입 주변 연결과 두께, 안구·속눈썹·치아·혀·입 내부를 정리합니다. 정면·45도·측면을 확인한 뒤 변형용 토폴로지를 확정합니다.
4. **애드온으로 페이스 리깅하고 검증.** 정리된 Tripo 모델에 얼굴 리그를 맞추고 웨이트·보정 표정을 조정합니다. 반쯤·완전히 감은 눈, 좌우 시선, 턱 열기, 미소, 시선과 깜빡임의 결합을 실제 모델에서 확인합니다. 템플릿 시험 통과로 이 단계를 대체하지 않습니다.
5. **머리카락·옷·장식 조립.** 쓸 수 있는 기존 부품은 재사용합니다. 다시 만들 머리카락은 사용자 검토를 거친 **전면·왼쪽·후면·오른쪽** 참조로 Tripo HD를 사용합니다. 제출 전 HD의 입력 지원을 확인합니다. 상단·하단 이미지는 내부와 실루엣 검수 자료로 사용합니다.
6. **부드러운 얼굴 동작·립싱크.** 입 모양을 만든 후 음성 신호와 연결하고, 전환 시간과 보간을 조정합니다. 눈 동작을 바꿨을 때 입 애니메이션이 사라지는 회귀도 확인합니다.
7. **GLB로 내보내 Godot에서 확인.** 필요한 뼈 동작과 셰이프 키 애니메이션을 내보냅니다. Blender에서 보이는 조작 기능이 게임에서도 자동으로 실행되는 것은 아니므로 실제 Godot 재생으로 판정합니다.

**다음 제작 목표는 Tripo 쇄골 흉상을 다듬고 애드온 페이스 리깅까지 적용한 시제품 한 개입니다.** MPFB로 만든 흉상은 별도 테스트이며 제작 기준본이 아닙니다. 얼굴 시제품 통과 후 몸·의상·게임 동작으로 넓힙니다.

2026-10-04 최신 제작: 승인 이미지로 P2 쇄골 흉상과 4방향 HD 헤어를 생성하고, 눈썹·위/아래 속눈썹은 간단한 UV 메쉬와 공유 RGBA 텍스처로 제작했습니다. `art/characters/explorer_b_hybrid_bust_v1/explorer_b_hybrid_bust_v1.blend`는 원본을 보존한 정적 조립 검토본입니다. 이번 Tripo 사용량은 140크레딧, 추가 승인 한도 잔여는 180크레딧입니다. 얼굴 색상은 검토용 정면 투영이며, 최종 UV·헤어 리토폴로지·페이스 리깅은 아직 완료되지 않았습니다.

### 눈썹·속눈썹·헤어 분리와 모발 표현

사용자는 눈썹·속눈썹·헤어를 각각 따로 제작하기로 했습니다. 얼굴의 위·아래 눈꺼풀 피부는 얼굴과 연결된 상태로 유지합니다. 대칭인 눈썹은 한쪽만, 속눈썹은 한쪽의 위·아래만 제작한 뒤 얼굴 중앙을 기준으로 미러 처리합니다. 좌우를 중복 생성하지 않습니다. 리깅에서는 좌우 표정을 독립 제어하고, 비대칭 가르마·앞머리는 원래 디자인을 유지합니다. 헤어는 두피·앞머리·옆머리·뒷머리를 구분합니다. 최신 결정은 **머리카락 Tripo HD / 얼굴과 나머지 생성 파츠 Smart Mesh P2 / 눈썹·속눈썹 간단한 Blender 메쉬 + UV + 알파 텍스처**입니다. 눈썹·속눈썹은 Tripo로 생성하지 않습니다. 새 이미지는 사용자가 검토한 후 3D 생성에 사용합니다.

| 이전 자료에서 확인한 기능 | 이번 제작에 적용할 제안 |
|---|---|
| Stefan P2 자막 03:15–04:36: 파츠별 생성과 폴리곤 수에 따른 헤어 결과 비교 | 헤어를 얼굴과 별도 생성. 강의의 1,500/3,000 예제는 비교 사례이며 모든 헤어의 고정 예산으로 사용하지 않음 |
| Stefan Sculpt 자막 09:09 이후: Mask Slice to New Object, Mask Slice, Grab/Elastic Grab, Clay, Smooth | 분리·마스킹 후 얼굴 관통부를 제거하고 두상에 맞춤. 속을 무조건 판으로 메우는 방식은 피함 |
| Stefan Texturing 힌트: Roughness와 별도 재질, 조명을 움직이며 확인 | 피부·눈썹·속눈썹·헤어 재질을 분리. 균일한 플라스틱 광택 대신 모발 결·광택 차이를 검토 |

그루밍 방향을 구체화하기 위해 Blender 4.5 공식 기능을 추가 확인했습니다. **Interpolate Hair Curves**는 가이드 사이에 모발을 만들고 밀도 마스크를 사용합니다. **Clump Hair Curves**는 모발 묶음과 끝 퍼짐을 조절합니다. **Attach Hair Curves to Surface / Deform Curves on Surface**는 표면 UV를 통해 뿌리를 연결하고 표면 변형에 따른 위치·방향 변화를 계산합니다. 현재 눈썹·속눈썹은 간단한 메쉬와 알파 텍스처 방식이 우선이며, 이 커브 기능들은 필요할 때 검토할 후보입니다. 아직 적용·검증 결과는 아닙니다. 커브와 지오메트리 노드를 그대로 게임 런타임 리그로 간주하지 않고, 게임용 메시·헤어 카드와 웨이트/표정 변형으로 변환한 뒤 Godot에서 확인합니다.

| **SQLite DB** | 서버가 관리하는 장부 | 계정·세션·소유권·작업 상태·진행·재화 기록. 현재는 서버가 직접 여는 파일 DB |
| **파일 저장소** | 실제 모델 파일 창고 | GLB 등 생성 결과 파일 저장. DB에는 경로와 해시 등 연결 정보 |
| **LLM** | 가구 설계와 제한된 동작 계획을 만드는 외부 서비스 | 입력을 부품 계획·동작 정의로 변환. 결과는 서버가 검증 |
| **Tripo** | 3D 모델 생성 외부 서비스 | 이미지·요청을 모델로 변환. 작업 ID로 진행 상태를 조회 |

현재 DB는 별도의 DB 서버 프로그램이 아니라 **SQLite 파일**입니다. 개발 환경의 기본 위치는 `server-data/world.sqlite3`, 개인 생성물 기본 위치는 `server-data/assets/`입니다. 운영 환경에서는 컨테이너의 데이터 볼륨에 저장합니다.

서버는 현재 **단일 Uvicorn 프로세스**를 전제로 동작합니다. 여러 서버를 동시에 늘릴 때에는 작업 잠금, 메모리 상태, DB와 파일 저장소 공유를 함께 설계해야 합니다. PostgreSQL·오브젝트 스토리지·별도 작업 큐는 향후 확장 후보이며 현재 설치 완료된 구성으로 표시하지 않습니다.

## 8. 실제 흐름 네 가지

### 8-1. 로그인하고 내 공간을 불러올 때

```text
① 클라이언트: 아이디·비밀번호로 로그인 요청
② 서버: 비밀번호 확인 → 세션 생성 → 로그인 토큰 반환
③ 클라이언트: 이후 요청 헤더에 Bearer 토큰 첨부
④ 서버: 토큰으로 사용자 확인 → DB에서 내 정보·집 상태·소유물 조회
⑤ 클라이언트: 허용된 정보와 모델을 받아 화면에 배치
```

비밀번호는 Argon2 방식으로 해시 처리하고, 세션 토큰도 DB에는 해시로 저장합니다. 요청에 다른 사용자 ID를 적었다고 그 사람의 소유물을 바꿀 수 있는 구조가 아닙니다. 서버가 로그인 정보를 기준으로 사용자를 결정합니다.

관련 API: `POST /v1/auth/login`, `GET /v1/me`, `GET /v1/homestead`. 클라이언트 연결 코드는 [api.gd](C:/lsm26/triphthonS1/game/scripts/api.gd), 서버 진입점은 [app.py](C:/lsm26/triphthonS1/server/app.py)입니다.

### 8-2. 생존하고 보상을 받을 때

```text
도전 시작 → 서버에 진행 생성 → 클라이언트가 이동·행동 입력 전송
       → 서버가 위치·시간·전투·생존 상태 계산 → 화면에 결과 반영
       → 종료 판정 → 보상 청구 → 재화 장부·진행 상태 저장
```

클라이언트가 “별씨를 이만큼 벌었다”는 최종 숫자를 마음대로 확정하는 방식이 아닙니다. 서버가 도전 결과를 판단하고 보상을 지급합니다.

응답을 받기 전에 연결이 끊겼다고 같은 보상을 두 번 받으면 안 됩니다. 이를 위해 변경 요청에는 `request_id`가 있으며, 동일 요청 재시도는 저장된 결과를 재사용합니다. DB의 거래 처리도 실패하면 되돌려 중간 상태가 남지 않게 합니다.

관련 API: `POST /v1/runs`, `POST /v1/runs/{id}/input`, `POST /v1/runs/{id}/claim`.

### 8-3. 공방에서 AI 가구를 만들 때

```text
플레이어 입력
  ↓
서버가 입력·잔액 확인 → 생성 작업을 DB에 기록
  ↓
LLM 설계 → 부품·동작 계획 검증 → 견적·임시 미리보기
  ↓
플레이어가 유료 생성 확인
  ↓
서버 작업 처리 → Tripo 요청 → 작업 ID 저장 → 진행 조회
  ↓
결과 파일 다운로드·검증 → 파일 저장소 + DB 소유권 등록
  ↓
클라이언트가 결과 조회 → 조립 정보·GLB 수신 → 보관·배치·색칠
```

**비용은 단계별로 구분합니다.** 작업 접수 시 게임 내 기본 비용이 먼저 차감·예약될 수 있고, 설계 단계에는 LLM 사용량이 발생할 수 있습니다. 현재 유료 Tripo 공방 경로에서는 견적 확인 후 실제 3D 생성 요청을 보냅니다. “확인 전에는 어떤 비용도 전혀 없다”고 설명하면 부정확합니다.

정적 가구는 하나의 메시를 중심으로 표시하고, 움직이는 가구는 여러 부품·회전 중심·제한된 동작 정의를 함께 사용합니다. 현재 부품 수는 최대 8개로 제한합니다. LLM이 작성한 임의의 Python이나 GDScript를 서버에서 그대로 실행하는 구조가 아닙니다. 서버가 제한된 문법과 연산을 검사합니다.

작업은 `queued → planning → awaiting_confirmation → building → ready`처럼 단계를 거칩니다. 실제 상태 이름과 실패·취소 분기는 구현에 따릅니다. 외부 요청의 성공 여부가 불명확하면 `unknown` 상태로 보존하며, 유료 요청을 자동으로 다시 보내지 않습니다.

주요 API: `POST /v1/studio/jobs` → `GET /v1/studio/jobs/{id}` → `POST /v1/studio/jobs/{id}/confirm` → 완료 후 `GET /v1/objects/{id}/assembly` 및 `/parts/{part_id}`. 동작·색·배치 변경 역시 별도 서버 API를 통합니다.

관련 구현: [asset_studio.py](C:/lsm26/triphthonS1/server/asset_studio.py), [provider.py](C:/lsm26/triphthonS1/server/provider.py), [design_provider.py](C:/lsm26/triphthonS1/server/design_provider.py), [model_loader.gd](C:/lsm26/triphthonS1/game/scripts/model_loader.gd).

### 8-4. 친구와 방문하거나 함께 생존할 때

```text
마을 초대 → 방문 수락 → 주인 포함 최대 3명의 야외 마을 산책
파티 초대 → 파티 수락 → 2–3인 협동 생존
                        각자 입력 → 하나의 공유 세계 상태 → 각 화면
```

마을 방문자는 현재 집주인의 야외 가구·작물을 **읽기 전용으로** 봅니다. 실내 방문은 현재 범위에 포함되지 않습니다. 협동 생존은 시간·맵·자원·적·모닥불을 공유하고, 체력·허기·기력·가방은 개인별로 관리합니다.

현재 통신은 **HTTP/HTTPS 주기적 요청(폴링)**입니다. WebSocket으로 항상 열린 실시간 연결을 사용한다고 설명하면 안 됩니다. 마을 위치 공유는 약 4Hz, 협동 입력은 최대 5Hz를 기준으로 하며, 화면은 받은 상태를 부드럽게 연결해 표시합니다.

서버가 협동 생존의 이동과 세계 상태를 판단합니다. 마을에서 클라이언트가 알려주는 위치는 방문 화면 표시를 위한 정보이며, 재화·소유권을 확정하는 근거와는 다릅니다. 재접속 처리와 입력 순서·유효시간 검사도 있습니다.

**검증 범위:** 기존 기록에 서버 테스트 138개 통과, 실제 Godot 클라이언트·계정 3개를 이용한 로컬 통합 검증, 패키지 실행 검증이 있습니다. 이 안내서 작성 중 다시 게임 테스트를 실행한 결과는 아닙니다. 최신 Google Cloud 서버 배포와 서로 다른 네트워크의 3인 검증은 남아 있습니다.

관련 구현: [multiplayer.py](C:/lsm26/triphthonS1/server/multiplayer.py), [coop.py](C:/lsm26/triphthonS1/server/coop.py), [social.gd](C:/lsm26/triphthonS1/game/scripts/social.gd). 상세 제한은 [멀티플레이 기록](C:/lsm26/triphthonS1/docs/MULTIPLAYER_20261004.md)에 있습니다.

## 9. DB에는 무엇이 저장되나

DB를 처음 읽을 때에는 **사용자 → 소유물 → 모델 파일**, **사용자 → 도전 → 보상**, **생성 작업 → 결과 소유물**의 세 연결부터 보면 됩니다.

```text
users (사용자)
 ├─ sessions / profiles / homesteads     로그인·프로필·마을 상태
 ├─ objects (내 소유물) ── assets        소유물과 3D 파일 연결
 ├─ runs / campaign_progress            도전과 이야기 진행
 ├─ ledger / requests                   재화 변경과 중복 요청 방지
 └─ 파티·협동 참여 기록                 함께 플레이하는 사람과 진행

studio_jobs (생성 요청과 진행)
 └─ 완성 결과 → objects + assets
                  ├─ studio_assets     조립 설명서
                  └─ studio_runtime    동작 상태·색·버전
```

이 그림은 이해를 위한 관계도입니다. 모든 연결이 단순한 외래 키 하나로 구현된 것은 아니며, 일부 게임 상태는 JSON으로 저장됩니다.

| 데이터 묶음 | 주요 테이블 | 쉽게 말하면 |
|---|---|---|
| 사용자·로그인 | `users`, `sessions`, `profiles` | 누구인지, 로그인 상태인지, 어떤 프로필인지 |
| 집과 진행 | `homesteads`, `campaign_progress` | 내 마을 상태와 이야기 진행 |
| 소유물·원본 파일 | `objects`, `assets` | 누가 어떤 물건을 소유하며 그 물건이 어느 파일을 쓰는지 |
| 생존 | `runs` | 도전 상태·결과·보상 수령 여부 |
| 재화·중복 방지 | `ledger`, `requests` | 별씨가 왜 변했는지, 같은 요청을 이미 처리했는지 |
| AI 생성 | `studio_jobs`, `studio_assets` | 생성 단계·비용·외부 작업 정보와 완성물 조립 설명 |
| 가구 사용 | `studio_runtime`, `furniture_locations`, `generated_apis` | 색·동작 상태·배치 공간·제한된 동작 정의 |
| 파티·방문 | `mp_parties`, `mp_members`, `mp_invites`, `mp_visits`, `mp_presence`, `mp_messages` | 파티·초대·방문 권한·현재 위치·메시지 |
| 협동 도전 | `coop_runs`, `coop_members` | 공유 도전 상태와 참가자별 상태·보상 |
| 후속 거래 | `listings` 등 | 판매 등록과 거래 처리를 위한 정보 |

`objects`는 **게임 안에서 소유·배치하는 물건**, `assets`는 **그 물건이 참조하는 파일 정보**입니다. `generated_apis`라는 이름도 별도의 자유로운 외부 서버가 생긴다는 뜻이 아니라, 생성 가구에서 허용할 동작 정의를 보관한다는 뜻입니다.

**DB 파일만 백업해서는 생성물을 완전히 복원할 수 없습니다.** 실제 GLB가 저장된 자산 폴더도 함께 보존해야 합니다. 컨테이너를 재시작해도 데이터가 남는 것과, 서버 장애 후 백업으로 복구가 검증된 것은 다른 상태입니다.

구조 근거: [database.py](C:/lsm26/triphthonS1/server/database.py), [asset_studio.py](C:/lsm26/triphthonS1/server/asset_studio.py), [multiplayer.py](C:/lsm26/triphthonS1/server/multiplayer.py).

## 탐험 수정 상세 · 기존 Claude 패치와 이번 수정

기존 Claude 커밋 `eba03e7bf1b6cdb6aaf26d510544744928c6e023`의 다음 9개 항목을 이번 실행 파일에 포함했습니다. 새로 제가 모두 발견·수정한 것으로 집계하지 않습니다.

## 설정 Esc·버튼 점검 · 2026-10-19 추가

- **재현한 오류**: 타이틀 → 설정 → Esc. 닫기 콜백이 설정창을 즉시 화면에서 제거한 뒤, 같은 입력 처리에서 `get_viewport().set_input_as_handled()`를 호출해 null 접근 오류가 발생했습니다. 재현 로그: `artifacts/settings-input-before.log`.
- **수정**: Esc 입력을 먼저 처리 완료로 표시한 뒤 창을 닫습니다. 물리 키 정보 없이 전달되는 Esc도 처리합니다. 키 변경 취소용 마우스 입력도 먼저 소비하고, 게임패드 B는 미저장 확인창을 취소하도록 맞췄습니다.
- **검증 방식**: 내부 닫기 함수를 직접 호출하는 검사에 더해 실제 키·마우스 이벤트로 설정 열기 → 수정 → Esc → 취소/버리기 → 재진입 → 적용 → 계속하기를 검사합니다. 타이틀, 마을, 탐험, 방 메뉴와 UI 140%·큰 글씨를 포함합니다.
- 별도의 영구적인 버튼 먹통 원인은 아직 확정하지 않았습니다. 로딩 화면이 클릭을 막는 동안 시험이 너무 일찍 클릭했던 경우는 구분했고, 로딩 완료 뒤 실제 버튼 동작을 확인합니다.
- 기존 설정 시험의 낮음 화질 기대값은 과거 80%가 남아 있어 현재 설정 75%와 맞췄습니다. 게임의 낮음 화질 값은 변경하지 않았습니다.
- **최종 결과**: 기존 설정 검사 268개와 출시 PCK를 사용한 실제 입력 검사 63개 모두 통과. 오류 로그 없음. 결과는 `artifacts/settings-original-after.log`, `artifacts/settings-input-packaged-after.log` 및 `settings-input-packaged-after-error.log`에 보관했습니다. 타이틀 Esc의 오류는 수정했고, 프로세스 강제 종료나 별도의 영구 버튼 먹통은 이번 검사에서 재현되지 않았습니다.

## 탐험 자동 공격 추가 점검 · 2026-10-19

사용자는 특별한 계기 없이 혼자 공격키를 누르는 현상이 있었다고 설명했습니다. 실제 키 입력을 게임에 보내지 않고 공격의 전역 눌림 상태만 남기는 시험에서 자동 공격이 시작됐습니다. 이전에는 매 0.43초마다 `Input.is_action_pressed("attack")`만 보고 공격을 예약하여, 남은 입력 상태와 실제로 게임에서 시작한 공격을 구분하지 않았습니다.

수정 전 13개 검사 중 8개에서 문제가 재현됐습니다. 채팅에 입력한 Space, 채팅·설정으로 끊긴 공격, 창 전환 뒤 남은 눌림 상태, 새 키 입력 없이 남은 공격 플래그를 포함합니다. 하드웨어나 엔진에서 처음 눌림 상태가 남는 원인까지 확인한 것은 아니며, 그 상태가 자동 공격으로 이어지는 경로를 차단했습니다.

- 게임 조작으로 전달된 **새 공격/채집 입력**만 연속 동작을 시작합니다. 전역 눌림 플래그 하나로 새 연속 동작을 시작하지 않습니다.
- 반복할 때 현재 눌림 상태와 실제 키 상태를 함께 확인하고, 키를 놓는 이벤트는 GUI 처리 전에 관찰합니다.
- 채팅 시작·종료, 메뉴 열기, 조작이 막힌 프레임, 월드 전환, 창 포커스 상실·복귀 시 연속 동작과 미전송 공격/채집 예약을 취소합니다.
- 조작을 다시 시작하려면 새로 눌러야 합니다. 키를 실제로 누르고 있을 때의 연속 공격과 짧게 한 번 누르는 공격은 유지합니다.
- 공격 키 재지정, 연속 채집, 한 번의 공격 애니메이션이 끝나는지도 별도로 검사합니다.

출시 PCK를 사용한 실제 입력·동작 검사 **19개 통과**, 오류 로그 없음. 설정 입력 63개와 협동 멀티 검사 38개도 회귀 통과했습니다. 재현·검증 스크립트: `game/tests/survival_attack_input_check.gd`. 근거: `artifacts/attack-input-before.log`, `attack-input-after.log`, `attack-input-packaged-after.log`. 같은 로컬 `0.11.9.5` 실행 파일을 다시 빌드했으며 운영 업로드는 하지 않았습니다.

## 생성 실패 진단과 LLM 전환

기존 OpenAI 경로는 여러 HTTP 오류를 `llm_request_failed`로 합쳤고, Gemini는 같은 회사 내 모델 재시도만 있었습니다. 새 코드는 다음 원인을 구분합니다.

| 원인 | 표시·동작 |
|---|---|
| 명시적인 정책 거절 | 정책 검사로 멈췄다고 안내. 구체적 사유가 없으면 임의로 추정하지 않음. 다른 모델로 재시도하지 않음 |
| Gemini RECITATION / IMAGE_RECITATION | 기존 자료와의 유사성 검사로 분리. 저작권 침해 판정이라고 표시하지 않음 |
| 429 요청 제한 / 5xx 과부하 | 원인 코드 분리. 설정된 다른 제공자로 전환 가능 |
| 시간 초과 / 연결 장애 | 각각 분리. 설정된 다른 제공자로 전환 가능. 앞선 호출의 사용량이 확인되지 않으면 미확정 표시 |
| 사용 불가능한 모델 | 설정된 모델·보조 제공자를 제한된 순서로 시도 |
| 잔액·지출 한도 부족 / 인증·권한 문제 | 운영 설정 문제로 종료. 자동으로 예산 제한을 넘기지 않음 |
| 설계 JSON·동작 검증 실패 | 기존 1회 수정 한도 유지. 다른 제공자로 무한 재시도하지 않음 |
| Tripo 생성·뼈대·애니메이션 실패 | LLM 실패와 구분. 이미 제출된 유료 3D 작업을 무조건 새로 제출하지 않음 |

OpenAI↔Gemini 전환을 구현했습니다. `TRIPOTHON_STUDIO_LLM`이 주 제공자이고, `TRIPOTHON_STUDIO_LLM_FALLBACKS=gemini,openai`가 보조 순서입니다. 중복 제공자는 제외하며 서버에 키가 있는 제공자만 선택합니다. 기본값은 빈 보조 목록입니다. 운영 키를 새로 발급하거나 운영 서버 설정을 변경하지 않았으므로 **운영 자동 전환 활성화는 아직 아닙니다**.

기존 유료 서버 구성 위에 추가할 `ops/compose.llm-fallback.yaml`을 준비했습니다. 서버의 `ops/secrets/openai-key`와 `ops/secrets/gemini-key`가 모두 준비되어야 합니다. 기존 배포 파일 목록의 마지막에 이 파일을 추가하면 됩니다. 키를 문서나 클라이언트에 넣지 않습니다. 실제 계정의 사용 가능한 모델은 별도 확인이 필요합니다.

모든 실제 호출·수정·전환은 기존 일일 호출 예산에 포함됩니다. 제공자별 시도와 오류 코드, 알려진 사용량을 저장합니다. 비용 집계에서도 전환 전후 토큰을 각 제공자에 귀속합니다. 타임아웃으로 사용량을 모르면 0원이라고 처리하지 않습니다. 원본 요청/비밀키/상위 서비스의 원문 오류를 새 진단 항목으로 노출하지 않습니다.

확인한 세 로컬 체크아웃의 기본 `server-data`에서 운영 제작 이력 DB를 찾지 못했습니다. 따라서 과거 실패가 저작권·심의·과부하 중 무엇이었는지는 아직 확인되지 않았습니다. 다음 실패는 새 코드와 시도 이력으로 구분할 수 있습니다. Tripo 자체의 가용성에는 여전히 의존합니다.

공식 근거: [OpenAI 오류 코드](https://developers.openai.com/api/docs/guides/error-codes), [Gemini 문제 해결](https://ai.google.dev/gemini-api/docs/troubleshooting), [Gemini 종료 사유](https://ai.google.dev/api/generate-content#FinishReason). 사용자에게 표시하는 분류와 전환 범위는 이 프로젝트의 구현 정책입니다.

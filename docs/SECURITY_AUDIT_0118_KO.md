## 결론과 범위

공개 가입 서버에서 가장 먼저 해결할 사항은 **LLM 호출의 별도 비용 한도 부재**, **콘셉트 호출의 불완전한 비용 기록**, **집 접근 제한과 자산 다운로드 권한의 불일치**다. 제작의 하루 5회 제한과 원장 기반 별씨앗 결제는 대체로 잘 보호되지만, 모든 유료 호출을 포괄하는 보장은 아니다. 이번 감사에서 critical 수준의 원격 코드 실행, 비밀키 탈취 또는 임의 관리자 승격은 확인하지 못했다. 이는 취약점 부재를 보증하는 결과는 아니다.

`CODEX_TASK.md`의 범위에 따라 작은 검증·횟수 제한·원장 수정만 적용했다. `server/multiplayer.py`는 원본 그대로이며, 관련 수정은 아래 제안으로만 남겼다. 커밋·푸시·배포·서버/VM 접속·외부 API 호출은 하지 않았다. 실제 운영 환경 변수, 키 잔액, 운영 DB와 로그는 열람하지 않았다. 문서의 “메인 서버 설정”은 `ops/README.md:85`에 기록된 5회/계정/일, 200별/제작, 200크레딧/제작, 서버 일일 횟수 제한 없음, 사용량 + 키 잔액 합계 90%의 예산 정책을 뜻하며 실제 배포값 확인 결과가 아니다.

처음에는 잘못된 sparse checkout 패턴 때문에 README와 작업 지시만 보였다. 현재 HEAD에서 감사 경로와 테스트가 참조하는 게임 파일을 이 작업 폴더에 복원했다. Git 설정은 변경하지 않았고, 기존 미커밋 소스 변경은 없었다. 아래 행 번호는 이번 수정 후 파일 기준이다.

### H1 — LLM 사용량이 공통 유료 생성 제한에 포함되지 않음

- 근거: `server/account_limits.py:6`, `server/interactions.py:65`, `server/interactions.py:667`, `server/interactions.py:691`, `server/interactions.py:730`, `server/interactions.py:760`, `server/asset_studio.py:868`, `server/design_provider.py:50`, `server/config.py:113`.
- 제작 횟수 집계는 `jobs`와 `studio_jobs`만 센다. `/v1/objects/{id}/interaction/describe`는 별도 `interaction_designs`에서 하루 10회를 세고 요청당 5별을 차감하지만, 제작 5회·서버 Tripo 예산·테스터 Tripo 예산을 검사하지 않는다. 실패한 설명은 별을 환불한다. 학습된 동일 설명의 캐시 적중은 실제 LLM 호출이 없어 문제 대상에서 제외한다.
- 공격 시나리오: 자기 소유의 제작 가구와 5별을 가진 일반 계정이 서로 다른 설명으로 캐시를 피하며 실패·수정 요청을 반복한다. 모의 공급자 재현에서 제작 작업 수가 1이고 서버 Tripo 사용량이 예산 200을 넘은 300인 상태에서도 **행동 설명 LLM 6회**가 실행됐고, 실패 환불 후 잔액은 다시 5별이었다. 별도 10회 한도는 유효하므로 이 경로를 계정당 무제한이라고 보지는 않는다.
- 설계 생성도 LLM 비용의 금액 예약이 없다. 일반 계정은 실패를 포함한 제작 5회에 묶이지만, 테스터는 제작 횟수 제한에서 제외된다. 설계 단계에서 실패하면 Tripo 예약 전에 종료되고 별을 환불한다. 모의 테스터에서 실패 설계 6회 후 테스터·서버 Tripo 집계가 모두 0이었다. 테스터 권한은 운영자만 부여하므로 공개 가입자가 이름만으로 이 예외를 얻지는 못한다.
- 설계 검증 실패 시 최대 2회 LLM 호출, Gemini의 모델 대체/재시도도 존재한다. 출력 토큰 상한 12,000은 호출당 제한이며 총비용 상한은 아니다. 사용자가 비싼 모델을 임의 선택하는 것은 live 제작의 모델/effort 고정 검사로 막힌다.
- 제안: 제작 설계와 행동 설명 모두 공통 LLM 비용 예약을 거치게 하고, 계정·테스터·서버별 예산을 별도 통화 단위로 정한다. 동시 호출 수와 재시도 비용도 예약한다. “5회”를 제작만의 횟수로 유지할지 모든 유료 AI 요청의 공통 횟수로 바꿀지는 운영자 결정이 필요하다. 별 환불과 실제 공급자 비용 기록은 독립시킨다.

### H2 — 콘셉트 실패·재생성·중단의 비용 기록 누락

- 근거: `server/asset_studio.py:188`, `server/asset_studio.py:496`, `server/asset_studio.py:690`, `server/asset_studio.py:718`, `server/asset_studio.py:731`.
- 기존 재생성 제한은 성공한 이미지의 `concept.draws`만 확인했다. 첫 이미지 성공 후 실패가 계속되면 새 `request_id`로 같은 작업의 재생성을 계속 요청할 수 있었다. 이는 새 제작 작업을 만들지 않아 제작 5회에도 추가로 잡히지 않는다.
- 수정: 재생성 승인 트랜잭션에서 `concept_redraw_attempts`를 저장하고 실패·불확실 응답도 시도로 센다. 첫 생성 이후 재생성은 최대 3회다. 기존 작업은 성공 횟수에서 시작값을 추정한다. 과거 실패 횟수는 기존 데이터만으로 복원할 수 없으므로 해당 작업은 배포 후 최대 남은 3회가 허용될 수 있다. 같은 `request_id` 재전송은 횟수를 추가하지 않고 병렬 요청은 하나만 승인된다. 재시작 후에도 제한이 유지된다. 성공 횟수 표시인 `draws`는 그대로여서 실패가 있었다면 화면상 최대 성공 횟수 전에 제한 오류를 볼 수 있다.
- 잔여 위험: 콘셉트 비용은 성공 결과 처리에 도달해야 부품에 누적된다. 실패 시 보고된 청구액은 테스터의 별도 기록에는 반영되지만 서버 집계에 쓰이는 부품의 누적 금액에는 빠질 수 있다. 모의 재현은 성공 5 + 실패 청구 5 = **실제 10, 서버 집계 5**였다. 불확실한 POST 또는 프로세스 중단에서는 호출/작업 ID 자체가 부품에 저장되기 전 유실될 수 있다. `planning` 중단은 실패·별 환불로 처리되어 공급자 비용이 없었다는 보장도 없다.
- 따라서 재생성 횟수 수정만으로 200크레딧/제작 또는 서버 총예산의 완전한 준수를 선언하지 않는다.
- 제안: 콘셉트·정제·메시마다 공급자 요청 전에 영속 예약을 생성하고, 불확실한 응답은 `unknown`으로 유지한다. 실패/취소/환불/삭제가 예약을 해제하지 않도록 한다. 공급자가 미청구 또는 미접수를 확인한 경우에만 운영자가 해제한다. 부품 하나의 `concept_task` 덮어쓰기 대신 시도별 작업 ID와 누적 실제 청구를 남겨야 한다.

### M1 — 실제 청구 초과 후 다음 부품 제출

- 근거: `server/asset_studio.py:668`, `server/asset_studio.py:947`, `server/asset_studio.py:994`, `server/account_limits.py:23`.
- 제작 확인 시 견적을 사용해 상한을 검사한다. 제출 직전 `reserve_build()`는 실제 청구와 남은 견적을 계산하지만 이를 테스터 예약에만 적용한다. 일반 계정의 서버 예산과 제작 크레딧 상한은 이 지점에서 재검사하지 않는다.
- 모의 공급자가 100크레딧으로 예상한 부품을 각각 150으로 청구하도록 했을 때, live 일반 계정의 제작/서버 상한을 모두 200으로 설정해도 두 부품을 제출하고 **300 사용, ready**가 됐다. 테스터의 실제 초과 기록·후속 제출 차단은 기존 테스트로 보호된다.
- 이는 플레이어가 공급자 청구 숫자를 직접 조작할 수 있다는 뜻은 아니다. 가격 변경·견적 오차·청구 이상이 생기면 공격자가 해당 제작 유형을 반복해 남은 예산을 소진할 수 있는 조건부 위험이다.
- 제안: 매 제출 직전 `이미 청구된 금액 + 현재 요청 예약 + 남은 부품 예약`을 공통 예산에 원자적으로 반영하고 초과 시 다음 제출을 중지한다. 이미 공급자가 청구한 초과분을 되돌릴 수는 없으므로 공급자 측 지출 한도·견적 여유도 함께 정해야 한다.

### M2 — 집 접근 제한과 개별 자산 권한 불일치

- 근거: `server/home_access.py:69`, `server/home_access.py:123`, `server/multiplayer.py:337`, `server/multiplayer.py:592`, `server/multiplayer.py:600`, `server/multiplayer.py:608`, `server/multiplayer.py:627`, `server/multiplayer.py:641`.
- presence 경로는 집 잠금·주인 부재·추방을 검사해 `space=null`로 거절한다. 하지만 `visible_object()`는 같은 마을 호스트가 배치한 집 가구라는 것만 확인하며 현재 집 접근 권한을 검사하지 않는다.
- 재현: 방문 중 집 가구 ID를 기억 → 주인이 문을 잠그고 방문자를 추방 → 방문자의 집 presence는 `reason=ejected`, `space=null` → 같은 가구의 `/v1/social/village/objects/{id}/model`은 **HTTP 200**. 같은 헬퍼를 쓰는 assembly/parts/paint도 코드상 같은 권한 공백이 있다. 모델 경로를 실제 로컬 재현했고 나머지는 공통 헬퍼 분석 결과다.
- 타인 집에 실제로 들어가거나 가구를 수정하는 권한까지 얻는 것은 아니다. 이미 다운로드한 파일을 회수할 수도 없다. 문제는 제한 이후에도 현재 자산을 계속 조회할 수 있다는 점이다.
- 제안 패치, 미적용: `visible_object()`에서 가구의 방도 조회하고, 방문 유효성·상호 차단·집 접근 상태를 공통 검사한다. 집 가구는 현재 승인된 집 presence가 있고 `home_access.state(...).open`일 때만 반환한다. 주인 자기 조회와 마을/NPC 가구 정책은 별도로 보존한다. GET에서 방문 TTL을 연장하지 않는다. “기존 손님은 잠금 후에도 머물 수 있음” 정책을 깨지 않도록 inside는 서버 저장 상태로만 계산한다. 모델/assembly/part/paint 각각에 잠금·추방·주인 이탈·방문 만료·차단 회귀 테스트가 필요하다.

### M3 — 이미지 검증 및 인증 전 처리

- 근거: `server/asset_studio.py:78`, `server/provider.py:136`, `server/provider.py:193`, `server/app.py:254`, `server/object_paint.py:54`, `server/object_paint.py:158`, `server/security.py:79`.
- 제작 참조 이미지와 GLB 내부 텍스처는 실제 포맷이 PNG/JPEG 중 하나인지만 확인해 서로 다른 MIME 선언을 허용했다. Pillow `verify()`만으로 픽셀 디코딩을 보장하지 않는다. 실제로 끝부분을 잘라 `verify()`는 통과하나 `load()`는 실패하는 JPEG를 재현했다.
- 수정: 선언 MIME과 실제 포맷 일치, 기존 크기 검사와 `verify()` 뒤 전체 `load()`를 요구한다. 공급자 이미지 미리보기는 픽셀 총량만 보던 검사를 보완해 한 변 4096 이하도 요구한다. 4097×1, 1×4097, 65536×1, 1×65536 입력을 거부한다.
- 제작 입력은 기존 1MiB, 한 변 16~2048 제한을 유지한다. GLB는 기존 파일 20MiB, 텍스처 한 변 4096, 총 24백만 픽셀, 메시/접근자/노드/인스턴스 예산을 유지한다. 따라서 큰 디코딩은 치수·픽셀 검사 전에 시작하지 않는다. 이미지로 가장한 비이미지, 외부 URI/확장/순환 노드/NaN/범위 밖 인덱스 방어도 기존 검사를 유지한다.
- 페인트는 기존에 PNG 서명·IHDR·1~1024 한 변·4MiB·전체 디코딩을 검사한다. 다만 페인트와 제작 참조 모두 인증 전에 이미지 처리가 가능했다. 수정 후 두 POST 경로는 미들웨어에서 세션을 먼저 확인한다. 인증 없는/만료된 토큰 요청은 이미지 파서를 실행하지 않고 401을 반환한다.
- 남는 한계: 본문 크기 미들웨어는 인증 검사보다 먼저 제한된 본문을 버퍼링한다. 인증 사용자도 반복 업로드할 수 있다. 대역폭·연결 수·본문 수신 시간에 대한 프록시 방어는 별도 운영 정책이다. 이미지 파서 라이브러리 자체의 알려지지 않은 취약점까지 검증한 것은 아니다.

## 제안 패치의 구현 기준

예산 관련 구조 변경은 다음 절차를 공통 헬퍼로 구현하는 것이 적절하다. 아래는 검토용 의사코드이며 적용한 코드가 아니다.

```text
BEGIN IMMEDIATE
  기존 attempt_id가 있으면 상태 반환 (POST 재전송 금지)
  계정/테스터/서버 예산에 실제 청구 + 미확정 예약 + 새 예약을 검사
  호출 종류(LLM/콘셉트/정제/메시), job, attempt, 상한, 상태=submitting 저장
COMMIT
공급자 POST 1회
작업 ID 수신 -> 예약에 즉시 저장; 불확실/중단 -> unknown 유지
청구 수신 -> 실제 금액 누적; 초과하면 후속 호출 차단
실패/별 환불/작업 삭제 -> 공급자 지출 기록은 보존
운영자가 미접수/미청구 증거를 확인한 경우에만 예약 해제
```

필수 검증은 동시 확인/재생성/다중 worker, 공급자 POST 전후 프로세스 중단, 429/5xx/타임아웃/잘못된 JSON, 실제 청구 초과, account 삭제/백업 복원, 재전송과 별 환불의 조합이다. 공급자의 idempotency 지원 여부는 이번 오프라인 감사로 확인하지 않았으므로 있다고 가정하면 안 된다.

우선순위는 H1의 공통 비용 정책 및 H2의 영속 예약, M2의 모든 자산 GET 권한 통일, M1의 매 제출 전 비용 재검사다. 잎전 마이그레이션·가입 보상 이전 제한·로그인 복구·위치 검증은 각각 데이터/사용자 경험 결정을 받은 뒤 별도 변경으로 진행한다.

## 검증 기록

- 모든 실행은 TestClient/모의 공급자/로컬 SQLite를 사용했다. 실제 유료 생성이나 네트워크 요청은 실행하지 않았다.
- 기존 전체 테스트: **1126개 통과**. 추가 회귀 파일: `server/tests/test_security_audit.py`, **25개 통과**.
- 추가 회귀 범위: 실패/불확실 콘셉트 재생성·request_id replay·재시작·병렬 승인, PNG/JPEG 형식 일치, 헤더 검사는 통과하는 잘린 JPEG, 긴/얇은 미리보기, 이미지 경계치, 인증 전 디코딩 차단, 가입 사전 검사와 병렬 할당 경쟁, 테스터 원장 지급과 예외 롤백.
- 별도 오프라인 재현 결과: 콘셉트 실제 10/집계 5, 실제 청구 초과 200상한/300사용, 집 추방 후 모델 200, 테스터 실패 설계 6회/Tripo 집계 0, 일반 계정 행동 설명 6회/제작 집계 1. 실제 공급자 청구나 운영 장애 관측값이 아니라 취약한 분기를 검증한 모의 결과다.
- 기본 pytest 임시 폴더는 sandbox 접근 거절로 처음 실행되지 않았다. 작업 폴더 안 `.audit-tmp`로 TEMP/TMP와 pytest basetemp를 지정해 실행했다. 제품 코드나 가상환경은 이 문제 해결을 위해 변경하지 않았다.
- 최종 전체 테스트: **1151개 통과, 실패 0, 경고 1**, 231.37초. 경고는 기존 Starlette TestClient의 httpx 사용 폐기 예정 안내다. `git diff --check`도 통과했다.

사용 명령(환경 변수는 해당 PowerShell 프로세스에만 적용):

```powershell
New-Item -ItemType Directory -Force .audit-tmp | Out-Null
$env:TEMP=(Resolve-Path .audit-tmp).Path
$env:TMP=$env:TEMP
$env:PYTEST_ADDOPTS='--basetemp=.audit-tmp/verified'
& C:\lsm26\triphthonS1\.tools\server-venv\Scripts\python.exe -m pytest server/tests -q
```

자동 승인 검토가 `.audit-tmp/`의 재귀 삭제를 정책상 차단하여 테스트용 임시 폴더가 남아 있다. 실제 운영 데이터나 키는 사용하지 않았다. 해당 폴더는 제품 변경에 포함하지 않는다.

변경 파일은 `server/app.py`, `server/asset_studio.py`, `server/provider.py`, `server/admin_cli.py`, 새 회귀 테스트와 이 보고서다. `CODEX_TASK.md`는 커밋하지 않았으며 어떤 파일도 커밋하지 않았다.

# Design critic

## Verdict
Each spec is strong on its own, but they cannot be merged as written. Sockets is mostly orthogonal and should run first, because the presentation is about in-game object creation. Social and UI overlap heavily and contradict each other: the same new files (chat_box.gd, social_window.gd, chat_box_check.gd), a SocialHub node versus a SocialHud CanvasLayer, chat placement, SocialChip, social-window side and tabs, the K label, notices versus toasts, and an empty versus a full social_features list. They must become one client social track before any code is written: state-only hub plus per-scene widgets, UI's layout and window stack, Social's server, channels and tabs.

All three collide in one place: input routing. main._unhandled_input and studio._unhandled_key_input need a single owner WP (U-WP-04) that sets the Esc/E/Enter/K priority, including seated ix exit. A second shared item is the Strict Presence model and its 422 fallback; one migration and one client negotiation layer should carry since/place and ix.

Every engine class or API the specs assume exists in 4.7.2. Verified: TwoBoneIK3D, LookAtModifier3D, RetargetModifier3D, ResourceLoader.list_directory, Animation.add_marker, modification_processed, static Basis.looking_at, DisplayServer.ime_get_text. The built-in LimitAngularVelocityModifier3D could replace the custom WP18 inertializer for NPCs.

The serious misses are these:
- **Stuck keys.** The engine drops the next key-up after an IME switch-off, so Input.action_release on focus exit does not fix stuck keys. A composition-aware release plus an echo watchdog is needed, or patched templates in the next reinstall.
- **Engine abort.** Calling DisplayServer.ime_get_text directly can abort the engine. Go through ImeCaret's guard.
- **Stray syllable.** ImeCaret re-inserts the pending syllable into the cleared chat field.
- **controls_enabled.** It is written at 10 sites, not 3.
- **Server tables.** The requests/audit tables grow without bound with always-on chat, and the chat delivery query runs inside the 4 Hz write transaction on a single worker.
- **Rebinding.** Users who already bound K get a duplicate key.
- **Untested modalities.** Gamepad, Chinese IME and reduced_motion are not tested.

Patch compatibility holds in all three: no project.godot or patch_boot.gd change, export_filter=all_resources ships .res/.png/.gd. Two conditions apply: K must stay a runtime-only action with the settings_check exemption, and clip discovery must be tested over a delta patch.

## Gaps
- IME stuck-key: both chat specs misread the bug. The template-only patch (tools/engine_patches/godot-4.7.2-ime-stuck-keys.patch, header) says that when a composition ends because the IME is switched off (focus leaves the field, a click, a window closes), the engine drops the NEXT key-up of ANY key, usually a W/A/S/D pressed later. Calling Input.action_release() in focus_exited (Social 3.2 rule 6, UI 6.2) runs before that lost key-up, so it cannot help. Social rules 4 and 5 and UI 'any window opening releases focus' will trigger it whenever a Hangul syllable is still open. Required: (a) when focus is released while ImeCaret.composing_text is non-empty, arm a watchdog for about 10 s; if a move action stays pressed with no echo key event for over 1.2 s (Windows typematic repeat), call Input.action_release. (b) Prefer releasing focus only after the composition has committed. (c) Put the patched templates in the next full-reinstall release. With always-on chat this bug also stands a seated player up or cancels a Sockets APPROACH, because HOLD exits on movement (Sockets section 5).
- Engine-abort guard: Social 3.2 rule 2 calls DisplayServer.ime_get_text() directly. ime_caret.gd (_ime_text, about lines 97-104) records that 4.7.2 aborts if asked before the window has ever had focus, and the call errors every frame headless. Read ImeCaret.composing_text or ImeCaret._ime_text(field) instead. That also honours ImeCaret.ime_override, which lets chat_box_check run headless.
- ImeCaret interaction not covered: on a focus change with an open composition, ImeCaret._on_focus_changed then _commit_to_origin (ime_caret.gd ~127-150) inserts the pending syllable back into the chat field after it was cleared and sent, so a stray syllable becomes the next draft. Separately, UI 6.2's 'await process_frame, then release' lets ImeCaret._process (an autoload, which processes first) call edit() again on the unedited field. That turns the IME on again (line_edit.cpp:138) and causes one more IME on/off cycle, which can arm the stuck-key bug. Use Social's synchronous release, and clear ImeCaret.composing_field/pending for the chat field on a successful send.
- Modalities nobody tests: (1) Gamepad. project.godot puts left-stick motion on the move actions, yet nothing opens chat or K from a pad. Sockets says 'movement input cancels APPROACH immediately', so stick drift above the 0.25 deadzone would cancel; use a magnitude threshold (walker_moving uses 0.3). (2) Chinese IME (zh is a shipped language): Enter during pinyin composition commits Latin letters and may or may not emit text_submitted. Test it with ime_type.ps1 too. (3) Alt-tab while typing or seated. (4) reduced_motion (game_settings.gd:603) is ignored by every chat fade, pop_in, notice and toast tween in both UI specs. (5) Mouse-only focus of the chat input: Social hides the input row in idle mode, so only the hint is clickable.
- player.controls_enabled is written at 10 sites in main.gd (548, 1061, 1103, 1584, 1600, 1740, 1752, 1970, 2772, 2961), not the 3 that Sockets WP4 names. Line 1061 sets it true unconditionally and 1752 sets it from screen alone. An interaction lock (ix_locked) and chat focus can therefore both be overridden. Add one main.refresh_controls() = world_movement_allowed() and not ix_locked(), and route every write through it, in the first WP that touches input.
- Rebinding collision: GameSettings.ensure_loaded (game_settings.gd:180-187) restores stored bindings per action. A player who already bound any action to K gets a duplicate K once 'social' arrives with default K. Add a migration pass: if K is already taken in the stored bindings, set social to KEY_NONE. Also test that apply_input creates the action before any is_action_pressed('social') call (tests/settings_check.gd:88-93 change).
- Server growth: mutate() (app.py:107-122) writes a requests row (with the JSON response) and an audit row for every chat line and every friends/social mutation. No code in server/*.py ever runs DELETE FROM requests or DELETE FROM audit. Always-on and global chat makes this unbounded on the 2 GB shared VM. Add retention: requests for operation 'chat' older than 24 h; audit for chat summarised or skipped.
- Server write-lock: Social 2.3 runs the chat delivery query and the friends_online COUNT inside the presence write transaction (multiplayer.py:236-248, BEGIN IMMEDIATE at 4 Hz per user, --workers 1 in ops/compose.yaml:56-57). The query shape `room IN (?,?,'global') OR (room='dm' AND (user_id=? OR to_id=?)) AND user_id NOT IN (subquery)` is not a single range on mp_messages_room(room,id) (multiplayer.py:36). Write it as a UNION ALL of per-room `room=? AND id>?` lookups plus the to_id index, or compute the reply after commit in db.read(). Budget it in the 60-poller load test (tools/test_multiplayer_load.py exists but has no chat or /people load).
- Adaptive 1 Hz polling (Social 2.8) is not reconciled with remote_motion. Its delay adapts over ARRIVALS=24 samples between DELAY_MIN 0.12 and DELAY_MAX 0.5 (remote_motion.gd:15-34), so switching cadence from 1 Hz to 4 Hz gives several seconds of laggy peers just when someone arrives. Sockets WP17 ix puppets ('t0' on the delayed playhead) inherit this. Also define 'alone' to include pending invites, party run status (can_join_run starts the run, social.gd:186-190) and peers on other floors in rooms.
- Feature detection plumbing: /health is read only at login (main.gd:759) and on a room return (main.gd:309). Rooms (studio.gd) never see health. social_features, interaction_sync and the chat2 cursor must be stored session-wide (in the hub) and passed to studio.gd. Neither spec handles a server redeploy mid-session that adds or removes a flag (re-read on a 422 or on version_gate).
- Static registries leak across scenes. UI's RpgUi.window stack, `static var window_listeners: Array[Callable]` and GameSettings.listeners keep Callables to freed scene nodes after a village-to-room change (rpg_ui.gd is a preloaded script, so static vars persist). top_window() and listener dispatch must prune invalid entries (is_instance_valid, Callable.is_valid()).
- Blocking vs party and village: neither spec defines what happens when you block a current party member (party chat and the shared run continue), or a peer who is still drawn in your village until the next poll. Block ends visits (Social 2.6) but not party membership.
- i18n: Social adds many tr() strings and about 15 new server error codes (chat_muted, whisper_target_unavailable, friend_*, knock_limited...) but lists no i18n/strings.json or error-map update; the pattern is the code map at social.gd:288 and main.error_message (main.gd:474). The en and zh catalogues will show Korean.
- Patch delivery checks missing: (a) Sockets WP9 tests discovery with --main-pack but not with a delta patch over a base (tools/game_patch.py --export-patch). It must also check that a file removed in a later patch (FILE_REMOVAL flag) does not appear in ResourceLoader.list_directory. (b) The new imported PNG (UI close.png, Sockets placeholder .res) should be confirmed in the patch with game_patch inspect. (c) export_filter=all_resources (export_presets.cfg:9) ships .res/.png/.gd but not new .json, so Social's server/data word list is fine but any client JSON is not.
- User-rule coverage: the UI spec has no Korean test doc per WP, no PNG layout figure (only an ASCII HUD, but plans-with-figures needs a PNG) and no roadmap update. The Sockets spec has no roadmap.json/build_roadmap.py step. The Social spec does not use the BenQ windowed-run rule (tools/test_window_position.ps1). All three should say that windowed captures are few (token-economy rule) and that sizes are reported (disk-usage rule).
- Presentation priority: in-game object creation is the main topic. UI WP-05 (craft window migration) and UI WP-04 (key routing rewrite) both touch the demo path (craft window C, E to sit). Neither spec freezes them before the talk.
- Bubble and nameplate anchoring: nameplates are fixed at y 2.05 (studio.gd:1571, social.gd), Social bubbles at a fixed 2.45, and Sockets defines an 'overhead' socket. Procedural lie keeps the body root high while the Root bone tilts, so labels float above beds. Sockets also wants a cancel 'icon bubble', and studio has resident_cues 2D bubbles (studio.gd:1999 pin_overlay) plus shadow_figure bubbles. That is four bubble systems with no shared pool.
- Engine facts all verified in D:/lsm26/engine/godot-4.7.2. None of the assumed classes or APIs is missing: TwoBoneIK3D, LookAtModifier3D, RetargetModifier3D and LimitAngularVelocityModifier3D are registered (scene/register_scene_types.cpp:679, 692, 699, 731); modification_processed (skeleton_modifier_3d.cpp:170); ResourceLoader.list_directory (core_bind.cpp:160) strips .import/.remap/.uid; Animation.add_marker (animation.cpp:4044); static Basis.looking_at with use_model_front (variant_call.cpp:2554); DisplayServer.ime_get_text (display_server.cpp:1665); Geometry3D.ray_intersects_triangle. Missed opportunity: LimitAngularVelocityModifier3D is built in. NPCs and shadow figures lack locomotion_pose's limiter, so they could use it instead of the custom WP18 inertializer.

Session state is a Node (Social: social_hub.gd, SocialHub.of(api)) versus a CanvasLayer 4 (UI: social_hud.gd, SocialHud.of(tree, api)). RESOLVE: one non-visual session node, social_hub.gd under tree.root on the CraftTracker pattern (craft_tracker.gd:51, 75), plus per-scene widgets under the scene's `ui`. That keeps main.hide_hud (main.gd:3322), the fold system, RpgUi.theme and the hud_fold_check:239 expectations working; a root CanvasLayer escapes all four. Merge UI WP-12/13/15 into Social WP3/4/5.
- Chat box placement. Social: village 360 wide with its bottom at y 690 above the hotbar; survival x14..284; rooms above RoomNav. UI: 328x226 with its bottom at 786 beside the hotbar, and RoomNav moved into the hotbar. RESOLVE: use UI's layout. The 7-slot admin hotbar is 586 px wide, centred, so it starts at x 347 (rpg_ui.gd:696-697) and 328 px clears it. Add UI's reflow at ui_scale 1.2-1.4. Note `expedition_button = bar.get_child(5)` (main.gd:1219) depends on slot order.

RESOLVE: retire it as UI proposes, but keep a node named 'SocialChip' (the header people button) so tests and fold_shift keep working.

UI: a left drawer 340 wide at y108..548 that can coexist with the bag, tabs 우리 마을/파티/초대 (+친구/접속 중). RESOLVE: use UI's left drawer, so it coexists with the right bag and does not hide the minimap. RESOLVE: UI's signature and tokens, with the channel colours added as tokens in rpg_ui.gd so the UI-17 lint passes. Pick one label. - Notices vs toasts. Social: a separate notice card stack at y 140, max 2, with buttons. UI: one toast lane at y 94, max 3, plus chat [url] links for invites. A stack of three pills from y 94 overlaps y 140. RESOLVE: one lane. Extend RpgUi.toast(kind='social', actions=[...]) so actionable cards persist 12 s inside the max-3 budget.
- Chat log rendering. Social uses one Label per line with a Tween per line and a 120-line ring. UI uses a RichTextLabel with escaped bbcode, [url] accept/decline links and 50 lines. RESOLVE: RichTextLabel (one node, cheaper on school PCs), append-only, rebuilt only when a new id arrives (UI risk note). Keep Social's channel chips and slash commands, which UI lacks (UI has only 마을/파티 tabs).
- Modal behaviour of chat. UI hides the chat box under any modal window and in dialogue. Social only releases focus (modal_card, open_dialogue, open_craft). RESOLVE: hide under modal windows through the window stack; hiding releases focus automatically (viewport.cpp:2555-2556). But apply the IME-composition guard, because hiding with an open syllable arms the stuck-key bug.
- Movement under drawers. Social and UI say non-modal drawers (social, bag) keep walking and chat live. Today world_movement_allowed returns false while the bag drawer is open (main.gd:2710), and key handling returns at main.gd:2909. Sockets ties controls_enabled to world_movement_allowed. RESOLVE explicitly: the social drawer does not block movement; the bag keeps blocking, or the change is made deliberately in UI WP-04 with tests. Route K before the main.gd:2909 early return.

In rooms: talk_box → craft → focused field → placement → resting stand → dock → pause (studio.gd:1647-1670). UI's chain is chat → window → drawer → placement → pause and omits seats. RESOLVE in one routing helper (UI WP-04, RpgUi.route_window_key): Esc goes chat field (the engine LineEdit consumes it, line_edit.cpp:940-946) → dialogue or modal top window → drawers, newest first → placement → ix.request_exit → pause. On the client, both rewrite the same 422 fallback (social.gd:153-155, studio.gd:1537), which today drops rich_presence (vx/vz/t) and loses that poll. RESOLVE: one server migration WP carrying both columns, and one client negotiation layer in the hub: presence_extra() per feature group, each gated by its own /health flag; a 422 drops the newest unconfirmed group first, then rich_presence.
- /health flags. UI section 7.4 adds `social_features: []` (empty). Social adds ['chat2','people','friends','visit','report'] plus global_chat. Sockets adds interaction_sync: 1. - Overhead space. Social's speech bubble at y 2.45, the nameplate at 2.05, the Sockets 'overhead' socket and its cancel icon bubble, studio resident_cues and shadow_figure bubbles. RESOLVE: one SpeechBubble pool anchored to ix_rig socket 'overhead' when present (fixed 2.05/2.45 fallback); a sockets icon bubble replaces any chat bubble on the same walker.

# 유료 생성 비용 보호

2026-10-16 · 보안 감사 H1, H2, M1 후속 수정

## 변경 내용

Tripo 콘셉트·참조 이미지 정제·메시 생성과 레거시 메시 생성은 공급자 요청 **전에** SQLite 트랜잭션으로 시도별 예약을 저장한다. `tripo_attempts`의 시도 ID마다 제작 ID, 계정 ID, 당시 테스터 여부, 종류, 부품 ID, 키 지문, 공급자 작업 ID, 예상 크레딧과 실제 청구액을 남긴다. 키 지문은 비밀키 자체가 아니다. 화면에서 현재 선택된 콘셉트를 바꾸더라도 이전 시도의 비용 기록은 덮어쓰지 않는다.

처음에는 `unknown`으로 예약한다. 작업 ID가 확인되면 `reserved`, 유효한 청구액이 보고되면 `charged`로 기록한다. 응답 불명, 프로세스 중단, 청구 정보 없는 종료는 미확인 비용을 남긴다. `charged`는 제작 성공을 뜻하지 않으며 실패한 작업의 청구도 포함한다. 실제 청구액은 늦게 증가할 수 있어 기존 기록보다 낮추지 않는다.

미해제 시도의 예산 점유액은 **예약액과 알려진 실제 청구액 중 큰 값**이다. 실제 청구액이 예약액보다 작거나 0이어도 자동으로 예산을 돌려주지 않는다. 작업 실패·취소·별 환불·계정 삭제는 이미 생성된 시도의 예약을 해제하지 않는다. 아직 공급자에 제출하지 않은 다음 부품의 예상 비용은 별도 `tripo_job_holds`에 보유하며, 제작 종료 시 이 미제출분만 정리한다.

개발 서버에서 서버가 직접 생성한 내장 무과금 Tripo 시뮬레이터만 예약액을 0으로 기록한다. 이 경우에도 시도와 작업 ID는 남긴다. 실제 공급자가 0을 보고하거나 설정 이름만 같다는 이유로 이 예외를 적용하지 않는다.

일반 계정과 테스터 모두 매 제출 직전에 `이미 발생한 시도의 점유액 + 이번 요청 예약 + 남은 부품 견적`을 제작별·서버 전체 예산과 비교한다. 테스터는 공유 테스터 예산도 검사한다. 검사, 예약 생성, 남은 견적 갱신은 같은 쓰기 트랜잭션에서 처리한다. 견적 100인 첫 부품에 150이 청구되면 한도 200에서 두 번째 100짜리 부품은 제출하지 않는다. 제작은 명확한 예산 오류로 실패하고 기존 별 원장 규칙에 따라 환불한다. 이미 발생한 공급자 청구는 유지한다.

제작 설계와 `/v1/objects/{id}/interaction/describe`는 `llm_call_reservations`를 공유한다. 비용 단위는 **LLM 호출 시도 예약 1회**이며 UTC 날짜별로 계정 한도와 서버 한도를 원자적으로 검사한다. 테스터도 이 한도의 예외가 아니다. OpenAI 설계 수정 요청, Gemini 모델 대체와 재시도는 실제 요청마다 추가 예약한다. 성공·실패·HTTP 오류·시간 초과·취소·중단 모두 집계하며 별 환불로 줄어들지 않는다. 설계 캐시나 행동 캐시 적중에는 예약하지 않는다.

LLM의 `reserved`는 전송 준비 단계, `unknown`은 전송 직전부터 응답 확인 전, `responded`는 응답 수신을 뜻한다. 응답의 성공 여부와 별개로 세 상태 모두 한도에 포함된다. 처음 예약한 뒤 키 누락 등으로 전송 전 실패한 경우도 보수적으로 1회 집계한다. 호출은 다음 UTC 날짜가 되면 새 일일 한도를 사용하지만 과거 기록은 삭제하지 않는다.

한도 오류는 LLM 계정 `llm_account_daily_limit`, LLM 서버 `llm_server_daily_limit`, Tripo 제작 `craft_over_trial_limit`, Tripo 서버 `tripo_budget_exhausted`, 테스터 `tester_credit_budget_exhausted`로 구분한다. 호출을 막아 제작·행동 설명이 실패하면 기존 규칙으로 별을 환불하지만 앞서 예약된 공급자 비용은 유지한다.

## 설정

설정은 모두 `server/config.py`에서 읽는다. 운영 서버 환경 변수는 이 작업에서 변경하지 않았다.

| 환경 변수 | 코드 기본값 | 의미 / 메인 서버 운영값 |
| --- | ---: | --- |
| `TRIPOTHON_LLM_USER_DAILY_CALL_LIMIT` | **20** | 새 설정. 계정별 UTC 하루 LLM 호출 예약 상한. 0이면 호출 차단 |
| `TRIPOTHON_LLM_SERVER_DAILY_CALL_LIMIT` | **1000** | 새 설정. 서버 전체 UTC 하루 LLM 호출 예약 상한. 0이면 호출 차단 |
| `TRIPO_USER_DAILY_REQUEST_LIMIT` | 5 | 기존 일반 계정 제작 횟수. 메인 서버는 5회/일 |
| `TRIPO_DAILY_REQUEST_LIMIT` | 5 | 기존 서버 제작 횟수. 메인 서버는 **0**으로 설정해 서버 일일 횟수 제한을 사용하지 않음 |
| `TRIPOTHON_MAX_CREDITS_PER_CRAFT` | 0 | 기존 live 제작별 Tripo 상한. 메인 서버는 **200** |
| `TRIPOTHON_TRIPO_CREDIT_BUDGET` | 0 | 기존 서버 누적 Tripo 예산. 메인 서버는 **29106** |
| `TRIPOTHON_TESTER_CREDIT_BUDGET` | 10000 | 기존 테스터 공유 누적 예산. 메인 서버는 **10000** |

새 LLM 설정은 0~1,000,000의 정수만 허용하며 무제한 값은 없다. LLM 한도 숫자는 운영자가 정한다. 기존 Tripo 설정의 0은 상한 비활성화이고 LLM의 0과 의미가 다르다. 기존 기본값의 호환성을 유지했으므로 메인 서버에서는 위 Tripo 운영값을 명시해야 한다. 서버 제작 횟수를 0으로 해도 LLM 일일 한도와 Tripo 누적 예산은 계속 적용된다.

## 운영자 사용량 조회

서버 데이터 경로에 접근할 수 있는 운영자가 로컬 명령으로 확인한다. 아래 명령은 공급자 API에 접속하지 않는다.

```sh
python -m server.admin_cli budget-usage --data-dir /data
python -m server.admin_cli tripo-reservations list --state unknown --data-dir /data
python -m server.admin_cli tripo-reservations list --data-dir /data
```

`budget-usage`는 다음을 JSON으로 출력한다.

- Tripo `charged`: 공급자가 보고한 실제 청구액. 실패 청구도 포함한다.
- `reserved`: 작업 ID/청구가 확인된 시도의 점유액에서 실제 청구액을 뺀 나머지.
- `unknown`: 미확인 시도의 점유액에서 알려진 실제 청구액을 뺀 나머지.
- `unsubmitted`: 아직 제출하지 않은 부품의 견적 보유액.
- `legacy_committed`: 새 시도 원장으로 전환되지 않은 과거 기록의 보수적 점유액.
- `committed`: 위 비용을 포함해 서버 예산 검사에 사용하는 전체 점유액. `tester_committed`는 테스터 공유 예산 집계다.
- 오늘의 LLM 호출 예약 수와 상태별 수, Tripo 점유액 상위 10계정, 오늘의 LLM 호출 수 상위 10계정.

계정별 순위는 영속 원장에 기록된 비용 기준이며 삭제 계정은 ID와 `deleted=true`, 이름 `null`로 표시한다. 아직 전환되지 않은 과거 비용은 전체 합계에 포함되지만 계정별 순위에서는 빠질 수 있다. 기존 `/v1/ops/usage`에도 `budget_safety` 집계와 적용 중인 LLM 한도를 추가했으며 계정 이름·ID·시도 ID는 공개하지 않는다. 기존 사용량 키 인증을 그대로 사용한다. Tripo 일별·전체 청구 통계는 새 원장의 실패 청구와 삭제된 작업의 청구도 포함한다. 기존 토큰 통계와 `runs`는 설계 기록 기반 통계이므로 새 호출 예약 수와 단위가 다르다.

## 미청구 예약 해제 절차

1. `tripo-reservations list`에서 시도 ID, 종류, 작업 ID, 키 지문, 금액과 상태를 확인한다. 해당 공급자 작업이 더 이상 실행 중이지 않은지 확인한다.
2. 공급자의 작업 기록·청구 기록 또는 고객 지원을 통해 **접수되지 않았거나 최종적으로 청구가 없었다는 사실**을 확인한다. 별 환불, 제작 실패, 계정 삭제만으로는 이 판단을 대신할 수 없다.
3. 확인 근거를 남겨 다음 명령을 실행한다. 근거에는 비밀키·토큰을 넣지 않는다.

```sh
python -m server.admin_cli tripo-reservations release ATTEMPT_ID \
  --confirmed-no-charge \
  --reason "공급자 문의 번호 ABC: 해당 요청 미접수 및 미청구 확인" \
  --data-dir /data
```

4. 같은 ID의 상태가 `released`로 바뀌고 `release_reason`, `released_at`가 저장됐는지 확인한다. `budget-usage`로 점유액을 다시 확인한다.

`--confirmed-no-charge`와 비어 있지 않은 사유가 모두 필요하다. 실제 청구액이 양수인 시도는 해제할 수 없다. 명령을 다시 실행해도 중복 차감하지 않는다. 기록 자체는 삭제하지 않는다. 공급자 미청구 확인은 운영자의 책임이며 명령이 외부에서 자동 검증하지는 않는다. 해제 뒤 늦은 양수 청구가 관측되면 비용을 다시 집계한다. LLM 일일 호출 예약은 이 명령으로 해제하지 않는다.

## 이전 데이터와 남은 위험

- 공급자가 예상보다 많이 청구한 **현재 요청**의 초과 비용을 서버가 취소할 수는 없다. 다음 요청을 차단하는 보호이며 공급자 측 지출 한도와 잔액 확인도 필요하다.
- 불확실한 요청을 다시 보내지 않는다. 응답 저장 직전 중단은 작업 ID가 없는 예약을 남길 수 있어 공급자 기록과의 수동 대조가 필요하다. 예약 후 실제 전송 전 중단도 보수적으로 비용을 점유한다.
- 과거 작업은 기존 견적·청구 집계를 유지한다. 과거 테스터 원장에 남아 있는 실패·삭제 작업의 예약도 서버 예산에 포함하며, 같은 작업의 기존 제작 집계와는 큰 값 한 번만 적용한다. 재개하거나 계정을 삭제할 때 과거 비용을 보수적인 `legacy_import` 예약으로 옮긴다. 이전 기록만으로는 각 시도를 복원할 수 없어 견적이 중복으로 보수적으로 잡히거나 재개가 한도에 막힐 수 있다. 이미 유실된 과거 실패·삭제 기록은 복구할 수 없다.
- LLM 일일 원장은 배포 이후의 호출 예약부터 기록하며 배포 이전 호출을 소급 복원하지 않는다. 배포 당일의 기존 사용량은 공급자 내역과 함께 확인해야 한다.
- LLM 호출 수는 금액이나 토큰 예산이 아니다. 모델 가격, 입력 길이와 출력 길이에 따라 같은 호출 수의 비용도 다르다. 호출당 기존 출력 상한과 공급자 지출 한도를 함께 사용해야 한다. 개발용 Codex 실행은 프로세스 호출 단위이며 내부 모델 동작은 이 원장에서 관측하지 않는다.
- 계정별 한도는 신규 다계정 생성을 막지 않는다. 공통 서버 한도가 전체 호출을 제한하지만 가입 제한과 운영 모니터링은 여전히 필요하다.
- 예약과 검사는 같은 SQLite DB를 쓰는 프로세스 사이에서 직렬화된다. 다른 DB·다른 서버·운영자가 직접 사용하는 공급자 키의 비용은 이 서버 원장에서 알 수 없다. 예전 DB 백업 복원 또는 구버전 서버로 되돌리기는 이후 비용 기록을 잃을 수 있으므로 공급자 내역과 재대조해야 한다.
- 실제 운영 서버, 비밀키, 공급자 API를 사용한 검증은 하지 않았다. 회귀 테스트는 로컬 SQLite와 모의 공급자로 실행한다.

# 0.11.9 의뢰 게시판·주민 편지 콘텐츠

주민 19명에게 일일 의뢰 문안 60개와 편지 40개를 배분했다. 한국어 원문과 영어(`en`), 중국어 간체(`zh`) 번역을 함께 제공한다. 의뢰마다 제목·부탁·수락·완료 대사가 있고, 편지는 짧은 일상 이야기를 담는다. 주민의 이름·직업은 `game/scripts/residents.gd`와 기존 주민 대사, 성격·취향은 `server/npc_homes.py`의 `NPCS`·`SENDERS`를 기준으로 삼았다.

의뢰 60개는 **기존 주민별 의뢰 19종의 조건을 공유하는 문안 변형**이다. 물건·수량·방문 장소·시간·완료 판정은 `server/quests.py`의 `QUESTS`에서 가져온다. 서버가 확인할 수 없는 새 재료, 제작 종류, 행동 조건을 만들지 않는다. 예를 들어 모카의 여러 부탁은 모두 사과 3개를 전달하면 완료되고, 보람의 부탁은 수락 이후 서로 다른 물고기 2종을 낚아야 한다.

## 파일과 연결

| 파일 | 역할 |
|---|---|
| `server/data/quest_templates_0119.json` | 의뢰 60개, 최상위 `version: "0.11.9"`, `templates` 배열 |
| `server/data/npc_letters_0119.json` | 편지 40개, 같은 버전과 `letters` 배열 |
| `server/quest_content.py` | JSON 로딩, 등장 회차별 의뢰 문안 선택, 편지 문안 조회 |
| `server/quest_board.py` | 기존 게시판 항목에 `content` 추가 |
| `server/npc_letters.py`, `server/npc_homes.py` | 기존 편지 종류에 맞는 `content` 추가 |
| `server/tests/test_quest_content_0119.py` | 100개 항목 검증과 게시판·편지 연결 회귀 검사 |

게시판의 기존 `id`는 계속 `moka_pie` 같은 진행·보상용 의뢰 ID다. `content.id`는 선택한 문안 ID이며, 수락·완료 API에는 기존 `id`를 보낸다. 날짜·주민·아이템·필요량·진행·별씨 보상은 기존 필드를 사용한다. 의뢰 `content.text[언어]`에서 `title`, `request`, `accept`, `complete`를 읽는다. 편지 본문은 `content.text[언어]` 문자열이다.

이번 변경은 서버 데이터와 작은 연결 코드에 한정한다. 게임 클라이언트 파일은 수정하지 않는다. 06은 게시판·편지 UI가 새 `content`를 읽도록 연결하고, 해당 문안이 없는 기존 편지는 기존 번역 키로 표시하면 된다. 이야기의 첫 선물 편지와 이번 묶음에 포함되지 않은 하트 편지에는 새 `content`가 붙지 않는다.

## 문안 선택과 편지 발송

게시판은 기존처럼 한국 시간 자정에 의뢰 5개를 교체한다. 같은 날의 조회·수락·완료는 같은 문안을 사용하고, 해당 의뢰가 다음에 다시 등장하면 그 주민의 다음 문안으로 넘어간다. 전체 문안이 실제 게시판에 등장하며, 계정이나 서버 재시작에 따라 무작위로 달라지지 않는다.

| `occasion` | 수 | 기존 연결 |
|---|---:|---|
| `request_done` | 19 | 게시판 완료 이벤트와 기존 일회성 의뢰 감사 편지 |
| `small_talk` | 5 | 해당 주민의 기존 하트 1~4 편지 본문 |
| `resident_day` | 13 | 기존 한국 시간 주민 기념일 발송 |
| `move_in` | 1 | 단비 입주, `move_in` 이벤트의 `kind: "in"` |
| `move_out` | 1 | 단비 퇴거, `move_out` 이벤트 |
| `came_back` | 1 | 단비 귀환, `move_in` 이벤트의 `kind: "back"` |

`small_talk`은 매일 읽어도 어울리는 일상 소재다. 새 일일 우편 발송이나 스케줄을 추가하지 않으며, 이미 있는 친밀도 편지에 연결한다. `resident_day`는 생일 분위기의 **마을 기념일**이며 캐릭터 생일을 새로 정하지 않는다. `came_back`은 콘텐츠 선택용 값이고 DB 이벤트 종류를 추가하지 않는다. 이전 `level` 기반 의뢰·이사 편지도 같은 문안으로 읽힌다.

## 의뢰·편지 예시

나루의 `quest_0119_naru_01`은 제목이 “표지판 친구들”인 방문 의뢰다. `quest_id`와 `reward_tier`는 모두 `naru_islands`, 분류는 `difficulty: "normal"`, `activity: "visit"`이다. JSON의 `request` 원문은 다음과 같으며, 응답에서는 `{count}`를 기존 조건인 `3`으로 바꾼다.

| 언어 | 부탁 본문 |
|---|---|
| `ko` | 다섯 섬 중 서로 다른 {count}곳의 표지판을 찾아가 봐. 길잡이의 작은 산책 숙제야! |
| `en` | Visit signposts on {count} different islands out of our five. A little walk from your guide! |
| `zh` | 去五座岛中不同的{count}座岛看看路牌吧。向导给你一份小小的散步作业！ |

한국어 수락 대사는 “광장부터 시작해도 좋아. 순서는 네 마음대로!”, 완료 대사는 “잘 다녀왔구나! 이제 표지판들도 너를 알아보겠어.”다. 실제 방문 후보는 기존 `square`, `fields`, `garden`, `camp`, `lighthouse`이며, 이 가운데 서로 다른 3곳을 방문하는 조건을 유지한다.

콩이의 일상 편지 `letter_0119_kid_small_talk`은 장난기 있는 성격과 연못에서 노는 일과를 따른다.

| 언어 | 본문 |
|---|---|
| `ko` | 연못 옆에서 내 그림자랑 누가 더 멀리 뛰나 겨뤄 봤어. 자꾸 같이 도착하는 걸 보니 꽤 좋은 짝꿍인가 봐! |
| `en` | By the pond, I challenged my shadow to see who could jump farther. We keep landing together, so I guess we make a pretty good team! |
| `zh` | 我在池塘边和自己的影子比谁跳得更远。每次都一起落地，看来我们是很不错的搭档！ |

단비의 귀환 편지 `letter_0119_shopkeeper_came_back`은 “다시 이 마을의 이웃이 되어 돌아왔어요! 짐을 풀다 익숙한 창밖 풍경을 보니, 장부 첫 장부터 기쁜 소식을 적고 싶어지네요.”라고 쓴다. 상인의 장부와 귀환의 반가움을 담으며 상점 할인이나 새 보상을 약속하지 않는다.

## 06의 수정 방법

1. 수정할 주민과 `id`를 찾아 세 언어의 `text`를 함께 고친다. 의뢰는 `title`, `request`, `accept`, `complete` 네 필드를 모두 유지한다. 한 문장의 분위기를 바꿔도 완료 조건이 달라졌다는 인상을 주지 않도록 실제 `QUESTS[quest_id]`를 먼저 확인한다.
2. `id`는 전체 두 파일에서 중복되지 않는 영문 소문자·숫자·밑줄 이름으로 유지한다. 기존 `quest_id`와 `npc`를 그대로 두며, `reward_tier`에는 해당 `quest_id`를 쓴다. 이는 기존 `STARS` 항목 참조이며 새 가격 등급이 아니다.
3. 의뢰의 `difficulty`는 `easy` 또는 `normal`, `activity`는 `gather`, `fish`, `farm`, `deliver`, `craft`, `visit`, `outfit`, `arrange` 중에서 고른다. 두 값은 콘텐츠 분류다. 수량·재료·시간·보상을 바꾸지 않는다. 채집/농사 의뢰도 실제 판정은 기존 가방의 해당 아이템 전달이다.
4. 수량을 문장에 넣을 때는 `{count}`를 사용할 수 있다. 같은 필드의 한국어·영어·중국어에 같은 placeholder를 같은 횟수로 넣는다. 서버가 기존 조건 수량으로 치환한다. 편지에는 placeholder를 사용하지 않는다.
5. 제작 문구는 기존 조건 안에서 설명한다. 노을은 실제로 빛나는 작품을 마을에 놓는 의뢰, 콩이는 `toy`·`animal` 태그의 작품을 콩이에게 선물하는 의뢰다. 새 제작을 강제하거나 음식 레시피·새 재료 ID를 약속하지 않는다. 기존 작품도 기존 완료 규칙에 따라 사용할 수 있다.
6. 편지는 `npc`, `occasion`, 세 언어 본문을 유지한다. 이번 40개에는 `gift_id`를 넣지 않았다. 선택적으로 넣는다면 기존 `npc_homes.RETURN_GIFTS`의 키를 사용해야 하며, 그 값은 콘텐츠 메타데이터일 뿐 지급 기능이 아니다. 실제 하트·이야기 답례품은 기존 `gift` 필드를 계속 사용한다.
7. 게임의 용어는 `game/i18n/strings.json`을 따른다. 별씨의 영어는 `Starseed`, 잎전의 영어는 `Leaf coin`이다. 금액·보상 제공을 새 대사에 약속하지 않는다.
8. JSON을 UTF-8로 저장하고 아래 검증을 실행한다. 서버는 시작할 때 JSON을 읽으므로 편집한 데이터를 확인할 때 서버를 다시 시작한다. 같은 주민의 문안 순서를 바꾸면 향후 등장 문안도 바뀔 수 있으므로 배열 순서는 의도적으로 관리한다.

현재 60/40 분포와 전용 테스트는 하나의 콘텐츠 묶음 계약이다. 문안을 더 추가하거나 편지 대상·이벤트를 늘릴 때는 수량·분포 테스트와 이 문서를 함께 수정하고 기존 훅으로 실제 도달 가능한지 확인한다.

## 경제·호환성·검증

기존 의뢰 보상 3~8 별씨와 배율·제작 보상 상한, 일일 수락/완료 각각 3회, 아이템 차감, 잎전, 친밀도, 답례품 지급, 발송 멱등성, 엔드포인트를 유지한다. 새 콘텐츠 로더는 DB에 쓰지 않는다. 편지 조회는 기존 `event`, `quest`, `story`, `move`, `gift`, 읽음 상태를 보존하고 대응하는 문안만 붙인다.

전용 테스트는 모든 의뢰 60개·편지 40개의 ID, 주민, 기존 아이템·제작 조건, 번역과 placeholder를 검증한다. 추가로 주민별 수량, 기존 기념일 일정, 전체 60개 순환, 같은 날짜의 선택 안정성, 호출자 수정으로부터 원본 보호, 게시판 수락/완료 및 구형·이벤트 편지 연결을 검사한다.

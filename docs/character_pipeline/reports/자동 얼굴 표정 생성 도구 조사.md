# 어떤 도구도 임의 얼굴의 52표정을 끝까지 자동화하지 못한다

2026년 10월 현재 상용 제품, 오픈소스, 코드를 공개한 연구를 모두 살폈지만, 실사·반실사·카툰·애니·괴물처럼 형태가 제각각인 3D 머리에서 **원본 메쉬를 그대로 둔 채 ARKit 52 셰이프키를 완전 자동으로 만들고, 상업적으로도 쓸 수 있는 도구는 하나도 없다.** 가장 가까운 후보는 셋이다. 상용 Blender 애드온 **Faceit**($78–99)은 원본 위에 52개를 굽지만 랜드마크 배치와 결과 수정이 사람 몫으로 남는 반자동 도구이고, 오픈소스 **QtMeshEditor `qtmesh facerig`**(MIT)는 완전 자동이지만 개발자가 구조상 사람형 전용이라고 못 박았으며, 신경망 **TopoRig**는 원본 토폴로지를 유지하는 자동 생성기지만 라이선스가 사내 상업 R&D까지 금지한다. 카툰과 동물까지 다루는 2025–2026년 연구(RigAnyFace, OmniFaceRig, RegHead, T2Bs)는 코드를 공개하지 않았고, Reallusion Headshot·MetaHuman·KeenTools 같은 대형 제품은 사용자 머리를 자기 템플릿 토폴로지로 바꿔 버려 우리의 원본 메쉬 유지 규칙과 정면으로 충돌한다. 가장 의미 있는 발견은 Meta의 2026년 OmniFaceRig가 도달한 구조, 즉 자동 얼굴 분할·키포인트에서 출발해 소수 템플릿 패밀리를 정합하고 고전 sparse deformation transfer로 표정을 옮긴 뒤 눈꺼풀·턱·충돌 규칙으로 마무리하는 구조가 tools/face_auto와 같은 축이라는 점이다. 템플릿 전략에 대해서도 문헌과 현장은 같은 답을 낸다. 사람 템플릿 하나로 모든 스타일을 덮는 방식은 실패 요인으로 반복 지적되고, 성공한 시스템은 **표정 어휘는 ARKit 52 하나로 고정하고, 기하 템플릿은 소수 패밀리로 두며, 눈 감기·입 다물기·입꼬리 같은 국소 문제는 얼굴마다 잰 값에 규칙을 적용해** 푼다. 따라서 지금 필요한 것은 새 도구 구매가 아니라 현재 엔진에 삼각형 단위 deformation transfer 잔차층, 스타일별 표정 기증 템플릿(ICT-FaceKit, hinzka의 VRoid 데이터, 자체 카툰 템플릿), 애니 전용 규칙을 붙이는 일이다. 이 조사는 Reddit이 차단된 상태에서 진행되어 Reddit 사용자 경험담을 담지 못했고, 어떤 도구도 우리 시험 머리 4개에 직접 돌려 보지 않았다.

## 상용 제품은 반자동 굽기와 템플릿 교체로 갈린다

상용 시장은 사용자 메시의 정점 위에 표정을 직접 굽는 도구와, 사용자 머리를 자기 회사 템플릿 토폴로지로 다시 표현하는 도구로 나뉜다. 셰이프키는 기준 메시와 정점 수가 같아야 하므로 리그로 포즈를 잡고 굽는 방식은 정의상 원본 토폴로지를 지키는 반면, 래핑·컨폼 방식은 얼굴 모양을 근사할 뿐 정점 집합은 업체 것이 된다.

첫 부류의 대표인 **Faceit**은 스스로를 반자동·비파괴 워크플로로 소개한다. 사용자가 얼굴 부위를 지정하고 랜드마크를 찍으면 랜드마크 기준으로 리그와 가중치를 맞추고 ARKit 52 프리셋 포즈를 셰이프키로 굽는다([Faceit 문서](https://faceit-doc.readthedocs.io/en/latest/), [Superhive Faceit](https://superhivemarket.com/products/faceit)). 사실형·의인화·카툰을 지원 대상으로 들고 토끼 캐릭터에 52개를 자동 생성한 예를 보여 주며, 2.3판은 임의 커스텀 리그와 비셈·FACS 같은 커스텀 표정도 받는다. 가격은 **$78(1.8) / $99(2.3) / $289(2–9석)**, 라이선스는 GPL이고, 평점은 80건 평균 5점이지만 초보자에게는 여전히 어렵다는 평이 붙는다([Faceit 평점](https://superhivemarket.com/products/faceit/ratings)). 약점은 두 가지다. **문서화된 Python API가 없고**, FAQ가 스스로 한계를 인정한다. 애니풍 평면 눈은 눈 뼈 피벗을 머리 안쪽으로 옮겨야 하고, 결과가 나쁘면 대개 랜드마크 탓이며, 가중치는 보통 정리가 필요하다. 또 셰이프키가 선형이라 굽고 나면 눈꺼풀이 안구를 뚫기 때문에, 눈 감기 중간에 드라이버로 눈꺼풀을 바깥으로 미는 보정 키를 넣으라고 권한다([Faceit FAQ](https://faceit-doc.readthedocs.io/en/latest/FAQ/)). 우리 T13은 랜드마크로 메타리그를 맞추고, 생성하고, heat 가중치를 주고, 포즈 라이브러리를 굽는 같은 흐름을 무료 Rigify로 헤드리스 재현해 이미 머리당 약 7분에 돌리고 있다(내부 문서 `11_T13_Rigify_얼굴`). 그러니 Faceit을 산다면 얻는 것은 새 기능이 아니라 품질 비교 기준선이다. 같은 부류의 저가 도구도 표정을 생성하지 않고 굽기만 자동화한다. **ShapeKeyGen**($15)은 Auto-Rig Pro나 Rigify 리그에 포즈 애니메이션을 깔고 사용자가 배율을 조정한 뒤 굽으며([ShapeKeyGen](https://superhivemarket.com/products/shapekeygen)), Shapekey Assist와 FaceFlex도 사람이 잡은 포즈를 굽는 도구다([Shapekey Assist](https://superhivemarket.com/products/shapekey-assist/docs), [FaceFlex](https://superhivemarket.com/products/faceflex)).

**Polywink**는 사용자 메시에 직접 전이한다고 내세운 유일한 상용 자동 서비스다. ARKit 52 패키지는 €299, 157 FACS 패키지는 €499에 24시간 안에 납품하며, 눈 뜨고 입 다문 neutral, 눈썹·속눈썹 제거, 별도 메시로 된 안구와 입안을 요구한다([Polywink iPhone](https://polywink.com/en/15-facial-animation-for-iphone-x.html), [Polywink BoD](https://polywink.com/en/9-automatic-expressions-blendshapes-on-demand.html)). 알고리즘 결과를 직원이 손으로 검수하고([80.lv](https://80.lv/articles/004adk-polywink-accessible-facial-animation)), 출시 때부터 대략 사람형 비율에서만 동작한다고 밝혔다([CG Channel 2018](https://www.cgchannel.com/2018/07/polywink-creates-blendshapes-and-rigs-for-any-head-model/)). 2026년 현재 홈페이지에는 점검 중이라는 배너가 걸려 있어 서비스가 돌아가는지조차 불확실하다([polywink.com](https://www.polywink.com/)). **NVIDIA Audio2Face**의 Blendshape Generation은 사용자 neutral에서 셰이프를 만들지만, NVIDIA 직원이 포럼에서 사용자 메시에 대한 52 ARKit 생성은 지원하지 않고 46 포즈 템플릿만 된다고 답했으며([NVIDIA 포럼](https://forums.developer.nvidia.com/t/how-to-export-arkit-blendshapes-weights/199713)), 앱 자체도 Omniverse Launcher와 함께 2025-10-01부로 지원이 끝났다([NVIDIA legacy tools](https://developer.nvidia.com/omniverse/legacy-tools)).

두 번째 부류는 원본 유지 규칙과 정면으로 충돌한다. **Reallusion Headshot 3**의 메시 모드는 원본을 4,000쿼드 CC 머리로 래핑하고, 매뉴얼은 가져온 메시가 참고용일 뿐 결과에 직접 영향을 주지 않는다고 밝힌다([Reallusion](https://www.reallusion.com/Character-Creator/headshot/3d-head-from-mesh.html), [Headshot 2 매뉴얼](https://manual.reallusion.com/Headshot_for_CC/ENU/2.0/06-Mesh-Mode/Quick-Guide-Mesh-Mode.html)). 2026-10-11 내부 시험에서는 큰 카툰 눈의 아래 눈꺼풀 점이 안구 한가운데에 찍혔고, 얇은 입술에서는 윗입술이 거의 사라졌으며, 사람 눈 크기에 맞춘 CC Eye_Blink가 높이 2.6 cm인 눈을 끝까지 감기지 못했다. **MetaHuman From Custom Mesh**는 표준 MetaHuman 토폴로지로 결과를 내고, 공식 문서가 강하게 스타일화되거나 비율이 극단적인 메시는 잘 풀리지 않을 수 있으며 평균에서 먼 캐릭터는 애니메이션 중 부피 손실이나 꼬집힘이 생길 수 있다고 경고한다([Epic 문서](https://dev.epicgames.com/documentation/metahuman/metahuman-creator-from-custom-mesh-tool-in-unreal-engine)). MetaHuman은 매출 $1M 이하 무료이고 상용 시스템 중 유일하게 5.7부터 공식 Python 배치 API를 갖췄지만, 정체성 solve와 오토리그가 클라우드에서 돈다([라이선스](https://www.metahuman.com/license), [5.7 릴리스 노트](https://dev.epicgames.com/documentation/metahuman/metahuman-5-7-release-notes), [From Mesh](https://dev.epicgames.com/documentation/metahuman/from-mesh)). **KeenTools FaceBuilder**는 자기 머리에 ARKit 호환 셰이프 51개를 주며 커스텀 모델 사용은 아직 안 된다고 답한다([KeenTools](https://keentools.io/products/facebuilder-for-blender)). 어떤 얼굴 메시든 된다고 홍보했던 **Ziva Face Trainer**는 실제로는 표준 점 순서로의 수동 리토폴로지를 요구했고 2024년 4월 단종됐다([CG Channel 2022](https://www.cgchannel.com/?p=138719), [CG Channel 2024](https://www.cgchannel.com/2024/04/unity-discontinues-the-ziva-products/)).

애니 틈새 제품도 같은 벽에 부딪힌다. **HANA_Tool**은 VRoid 머리에 Perfect Sync 52개를 한 번에 붙이지만 VRoid끼리 정점 정보가 같아서 가능한 일이고, 메시를 고치거나 데시메이트하면 정점 수 불일치 오류가 난다([HANA_Tool v5](https://booth.pm/en/items/4607357), [VSeeFace](https://www.vseeface.icu/)). Unity용 **FaceTra Shape Creator**는 메시 모핑으로 페이스트래킹 셰이프 작업의 상당 부분을 자동화하고 애니풍 아바타를 주 대상으로 설계됐지만, 처음에는 다루기 거칠다고 스스로 밝힌 Unity 에디터 도구다([hai-vr 문서](https://docs.hai-vr.dev/docs/products/facetra-shape-creator)).

시장 가격은 자동화의 가치가 어디 있는지 드러낸다. Fiverr의 $10–25짜리 하루 납품 상품은 .vroid 파일을 요구하는 VRoid 템플릿 적용이고([Fiverr](https://www.fiverr.com/bottegastrega/add-blendshapes-to-your-avatar-for-perfect-sync-android-and-iphone)), 커스텀 스타일 모델은 $45–100 이상에 몇 주를 기다려야 한다([VGen](https://vgen.co/v_risalab/service/custom-arkit-blendshapes-for-3d-model/34facee4-17ef-4646-9663-fb1dbf8d5e7f)). 일본 Coconala의 한 판매자는 첫 모델에 ¥5,000, **같은 얼굴 메시를 쓰는 추가 모델에는 ¥500**만 받으면서 케모노·로봇형은 받기 어렵다고 적었다([Coconala](https://coconala.com/services/1648942)). 비용은 거의 전부 새 얼굴 형태에서 나오고, 그 지점이 바로 상용 도구가 실패하는 스타일화·비인간 얼굴이다.

## 오픈소스는 사람형에서만 끝까지 자동이고, 가장 강한 모델은 상업 금지다

오픈소스에서 neutral 머리를 넣으면 표정 세트가 나오는 도구는 셋이고, 셋 모두 사람 템플릿인 ICT-FaceKit의 표정 공간에 뿌리를 둔다. **QtMeshEditor `qtmesh facerig`**는 CLI 한 번으로 사용자 머리에 ARKit 모프 타깃 52개를 붙인다. 내부적으로 ICT-FaceKit 템플릿을 NRICP로 맞추고 삼각형별 deformation transfer로 옮기는 결정론적 희소 선형 풀이이며 신경망이 아니다. 출력은 원래 메시에 표정을 얹은 것이고, 코어는 Ogre 없이 헤드리스 단위 시험을 거쳤으며, 라이선스 문제로 FLAME과 Wrap3D를 일부러 배제하고 MIT인 ICT 템플릿을 택했다([epic #889](https://github.com/fernandotonon/QtMeshEditor/issues/889), [저장소](https://github.com/fernandotonon/QtMeshEditor)). 그러나 같은 문서가 사람 ARKit 템플릿에서 옮기는 DT는 대략 사람형 얼굴에서만 의미가 있고 소품·네발짐승·비얼굴 메시에서는 쓸모없는 결과가 나온다고 명시한다. 구조로 보면 이 도구는 우리 face_fit(TPS + 대칭 NRICP)에 **조밀 DT 단계를 더한 것**과 거의 같다.

**TopoRig**는 FACS 컨트롤에서 정점별 변위를 예측하는 신경망으로, ICT FaceKit 표정 모델에서 출발해 생성한 정체성 3,496개로 학습했고 입력 메시 정점을 원본 토폴로지 그대로 직접 변형한다([arXiv 2609.15746](https://arxiv.org/abs/2609.15746)). 입력 정렬은 Blender 백그라운드에서 MediaPipe 랜드마크로 자동 처리하지만, 선택 후처리인 입술 분리·치아·혀 추가와 안구 교체는 형상을 바꾸고, 카툰·애니 평가는 없다([README](https://github.com/TaatiTeam/TopoRig)). 결정적인 것은 라이선스로, TopoRig Academic Use License는 상업 사용을 금지하면서 그 범위에 "internal commercial research or development"까지 넣었다. **상업 프로젝트라면 사내 비교 실험조차 허용 범위 밖**이라는 뜻이다. **NFR**(SIGGRAPH 2023)은 코드가 MIT지만 사전학습 데이터 일부인 Multiface가 CC-BY-NC 4.0이라 가중치의 상업적 지위가 불명확하다([NFR 저장소](https://github.com/dafei-qin/NFR_pytorch), [Multiface](https://github.com/facebookresearch/multiface)). 입력 메시에는 입·눈·코 소켓과 안구가 없어야 하고 입과 눈이 잘려 있어야 하며 `align.blend`로 손수 대략 정렬해야 하고, 공식 지원 OS는 Ubuntu뿐이다. 학습 데이터가 사람뿐이어서 후속 연구들은 NFR이 스타일화 메시에서 눈썹 이동과 스케일 변화 아티팩트를 내고 비인간형 머리는 거의 변형하지 못한다고 보고했다([NFS](https://arxiv.org/html/2505.22416v1), [RigAnyFace](https://arxiv.org/html/2511.18601v1)).

이 셋 아래에는 부품 라이브러리가 있다. Sumner–Popović deformation transfer 구현체로는 마커 고정 대응 단계까지 들어 있는 [mickare](https://github.com/mickare/Deformation-Transfer-for-Triangle-Meshes)(MIT), 순수 Python인 [vasiliskatr DT](https://github.com/vasiliskatr/deformation_transfer_ARkit_blendshapes)(MIT), C++ 헤더 전용 [deformxfer](https://github.com/jerenchen/deformxfer)(BSD-3)가 있으나 대부분 2021–2022년 이후 휴면 상태다. vasiliskatr 저장소의 ARKit 원본 메시(Kite & Lightning)는 데모 전용이라 출시용으로는 ICT-FaceKit 같은 허용 라이선스 원본으로 바꿔야 하고, 같은 저자의 [Example-Based Facial Rigging 재구현](https://github.com/vasiliskatr/example_based_facial_rigging_ARkit_blendshapes)(MIT)은 템플릿 셰이프와 타깃 예제 포즈가 같은 토폴로지일 것을 요구한다. NRICP는 활발히 유지되는 [trimesh](https://github.com/mikedh/trimesh)(MIT)의 `nricp_amberg`로 대체할 수 있다.

Blender 쪽에서는 두 저장소가 우리와 특히 가깝다. **CaptureForge**(GPL-3)는 머리를 렌더해 MediaPipe 랜드마크를 찾고, 그것으로 경량 얼굴 리그나 Rigify 얼굴 메타리그를 자동으로 맞춘 다음, ARKit 마커별 포즈를 `evaluated(pose) − evaluated(neutral)`로 굽는다. 부드러운 좌우 분할과 뒤집힌 법선·찌그러진 삼각형·대칭을 보는 품질 검사기도 있고 모든 기능이 `blender --background`로 도는 함수지만, 스타일 머리에서 MediaPipe가 얼굴을 못 찾으면 수동 도움이 필요하다고 적었고 별 1개짜리 신생 저장소다([CaptureForge](https://github.com/H0wZy/captureforge)). **mdj128/facial-animation**(Tripo Face Rig, MIT)은 Tripo가 생성한 머리에 측정이 허락하는 곳마다 턱·혀·눈·눈썹 뼈를 넣고 절차적 셰이프키, 입안, ARKit·VRChat 초안을 Blender 5.1.1 CLI로 만든다. 다만 스스로 실험적인 아티스트 보조 도구라 부르고, 입 검출과 얼굴 가중치는 캐릭터마다 눈으로 검토해야 한다고 밝힌다([저장소](https://github.com/mdj128/facial-animation)). 목표가 우리와 거의 같아서 비교 대상으로 읽어 볼 가치가 있다. 애니의 유일한 자동 경로는 VRoid 정점 순서 복사인데, hinzka의 52 Perfect Sync 데이터는 README에서 개인·상업 이용과 재배포·판매를 출처 표기 없이 허용한다([hinzka](https://github.com/hinzka/52blendshapes-for-VRoid-face)). 다만 VRoid 샘플 모델에서 파생된 데이터라 그 기반 메시의 권리가 우리 용도를 막는지는 확인하지 못했다.

이름과 실제가 다른 저장소도 있다. [mediapipe-arkit-automesh](https://github.com/arturwyroslak/mediapipe-arkit-automesh)는 빈 키에 jawOpen 가짜 변형 하나만 넣는 데모 스텁이고, [blender-copilot](https://github.com/dwgx/blender-copilot)의 절차적 모드는 머리 바운딩 박스의 고정 비율로 영역을 찍는다. UniRig, MagicArticulate, Puppeteer 같은 rig-anything 모델은 몸 골격만 만들며([UniRig](https://github.com/VAST-AI-Research/UniRig)), T2Bs 저자들도 이 골격들이 얼굴 모션에 맞지 않는다고 판정했다([T2Bs](https://arxiv.org/html/2509.10678v2)). 2025년 공개된 Audio2Face-3D는 SDK가 MIT이고 모델이 상업·비상업 모두 허용하는 NVIDIA Open Model License지만, 새 메시에 셰이프를 만들어 주지는 않고 이미 있는 블렌드셰이프 세트의 가중치를 풀 뿐이다([허브](https://github.com/NVIDIA/Audio2Face-3D), [모델 카드](https://huggingface.co/nvidia/Audio2Face-3D-v3.0), [논문](https://arxiv.org/html/2508.16401v1)). 52개가 완성된 뒤 립싱크를 구동하는 단계에서 쓸모가 있다.

템플릿 자원의 라이선스는 이렇게 정리된다. ICT-FaceKit의 light 모델은 MIT이고 ARKit 이름을 쓴 좌우 분리 표정 53개를 갖는다([ICT-FaceKit](https://github.com/USC-ICT/ICT-FaceKit)). Microsoft Rocketbox는 MIT이고 ARKit 호환 블렌드셰이프를 공개했지만 보관(archived) 상태다([Rocketbox](https://github.com/microsoft/Microsoft-Rocketbox)). FLAME은 출처끼리 말이 다르다. 사이트 공지는 FLAME 2023 Open을 CC-BY-4.0으로 공개했고 이전 버전은 비상업 전용이라고 하지만([FLAME](https://flame.is.tue.mpg.de/)), 모델 라이선스 페이지는 여전히 비상업 조항을 보여 준다([FLAME 라이선스](https://flame.is.tue.mpg.de/modellicense.html)). 어느 쪽이든 FLAME은 PCA 표정을 쓰고 사용자 토폴로지를 대체하므로 우리 용도와는 거리가 멀다.

## 2025–2026 연구는 카툰·동물로 넓혔지만 결국 템플릿 패밀리와 규칙으로 돌아왔다

학술 계보는 기하 전이 계열, 메시에 의존하지 않는 신경 리깅 계열, 2025–2026년의 전자동 파이프라인 계열로 정리된다. 이미 리그가 있는 캐릭터의 가중치를 구하는 리타게팅 연구도 있지만, 그것은 셰이프 생성이 아니라 구동 문제를 푼다.

기하 전이 계열의 뿌리는 Sumner & Popović의 Deformation Transfer(SIGGRAPH 2004)다. 소스의 삼각형별 affine 변형을 정점 수와 연결성이 다른 타깃에 다시 적용하며, 선형 시스템을 한 번 분해해 두면 새 표정은 back-substitution만으로 얻는다([프로젝트](https://people.csail.mit.edu/sumner/research/deftransfer)). Disney(2022)는 DT가 개별 요소 단위로 작동해 아티팩트가 생기기 쉽다고 비판했고([Disney Research](https://studios.disneyresearch.com/2022/07/24/local-anatomically-constrained-facial-performance-retargeting)), 이를 보완하는 방향이 두 갈래로 나왔다. Semantic DT(2009)는 짝지은 예제 포즈 몇 쌍(그림 1은 5쌍)으로 두 형상 공간을 이어, 사람 걷기를 홍학에 옮길 때 무릎이 반대로 굽는 것처럼 기하보다 의미를 보존한다([논문](https://homes.cs.washington.edu/~jovan/papers/baran-2009-sdt.pdf)). Example-Based Facial Rigging(Li, Weise, Pauly 2010)은 일반 템플릿의 컨트롤 의미를 유지한 채 타깃의 예제 포즈를 재현하도록 블렌드셰이프를 gradient 공간에서 최적화하며, **훈련 포즈가 1개여도 그럴듯한 결과**를 낸다([EPFL](https://infoscience.epfl.ch/record/149375)). Expression Packing(2020)은 그 예제 포즈를 최소한으로 고르는 방법을 준다([EG DL](https://diglib.eg.org/handle/10.1111/cgf13925)).

신경 리깅 계열은 사람 데이터의 벽에 막혀 있다. NFR의 후속작 NFS(KAIST + Flawless AI, Eurographics 2025)는 정점별 skinning 가중치 인코더를 더해 로컬 디테일을 지키고 ICT 오차를 0.3514에서 0.2480으로 줄였지만, 스타일화 데이터 없이 학습했고 스타일화 얼굴(Mery, Bonnie 등)은 정성 평가만 했으며, 저자 스스로 **타깃 스케일이 학습 분포와 다르면 skinning 가중치가 부정확해진다**고 적었다([NFS](https://arxiv.org/html/2505.22416v1)). RigAnyFace(Penn State + Roblox, NeurIPS 2025)는 이 벽을 데이터로 넘으려 했다. 리그가 있는 머리 161개와 리그가 없는 머리 175개를 쓰되 리그 없는 머리는 2D 얼굴 애니메이션과 optical flow로 감독했고, 안구 같은 분리 컴포넌트를 위한 전역 인코더를 붙여 테스트 때 템플릿·랜드마크 없이 T4 GPU에서 3.1초 만에 결과를 낸다. 그래도 정량 평가는 인간형만 했고, 디테일 없는 껍데기형 메시나 여러 조각으로 쪼개진 메시에서는 무너진다([RigAnyFace](https://arxiv.org/html/2511.18601v1)). 코드는 공개되지 않아 OmniFaceRig 저자들도 RAF를 재실행할 수 없었다고 적었다.

가장 중요한 결과는 **OmniFaceRig**(Meta Reality Labs, 2026)다. 구강이 없는 표면 메시를 받아 FACS 블렌드셰이프를 최대 155개 만들고 치아·잇몸·혀를 절차적으로 생성한다. 먼저 VLM과 CV를 섞어 리깅 가능한 메시인지 검사하고, 스타일 인간용 41클래스 파서와 비인간용 38클래스 파서, SAM 3 폴백으로 얼굴을 분할한다. 이어 코를 제외한 조밀 키포인트로 템플릿을 정합하고, 치아를 RBF로 휘어 ARAP과 SDF로 배치해 입안을 만든 뒤, 충돌을 고려한 **sparse deformation transfer**로 표정을 옮긴다. 마지막으로 Point Deform과 Delta Mush로 다듬고 눈꺼풀 닫힘·시선·턱·치아-얼굴 충돌 규칙을 적용한다. 템플릿은 **사람, 긴 주둥이(개·늑대·여우·말), 짧은 주둥이(고양이·곰·토끼·호랑이) 3종**이고 자산마다 VLM이 고른다. 인간·인간형 300개에서 성공률 99.0%, 자산당 20–30초를 기록했지만, 저자들은 이것이 모든 동물·스타일화 캐릭터를 덮는 일반 파라미터화가 아니며 새 부리, 물고기 입, 곤충 겹눈, 해마 주둥이에서 실패한다고 분명히 했다([OmniFaceRig](https://arxiv.org/html/2606.08043)). 프로젝트 페이지에 코드는 없고, 공개하겠다던 벤치마크 데이터도 아직 준비 중으로 표시돼 있다([프로젝트 페이지](https://omnifacerig.github.io)). 신경망을 다뤄 본 산업 연구소가 2026년에 고른 엔진이 2004년의 DT에 규칙을 더한 것이라는 사실은, tools/face_auto가 걷는 원본 보존·영역 컷·측정 기반 규칙의 길이 연구 최전선과 같은 축에 있다는 근거다.

Snap 쪽 생성형 연구는 데이터 문제를 다르게 푼다. **RegHead**(2026)는 소수의 아티스트 리그 라이브러리로 미세조정한 이미지 편집 모델(Qwen-Image)로 표정 이미지를 만들고, 이미지 조건 3D/4D 생성으로 표정 메시를 재구성한 뒤 사람이 검수해 약 2만 개로 늘린다. 그다음 피드포워드 정합기가 neutral을 기반으로 약 5초 만에 블렌드셰이프를 뽑지만, 어휘가 **표정 7개**뿐이고 국소적인 미소·찡그림은 잘 재현하지 못한다([RegHead](https://arxiv.org/html/2607.12206)). **T2Bs**(ICCV 2025)는 텍스트로 메시를 만들고 비디오 확산 모델로 표정 영상 20개를 만든 뒤 PCA로 블렌드셰이프화하며, 비인간 얼굴에 사람 랜드마크 검출기가 맞지 않아 VLM으로 눈과 입을 분할했다([T2Bs](https://arxiv.org/html/2509.10678v2)). RegHead의 흐름은 우리가 T7에서 Tripo 표정 스캔을 neutral에 정합한 것과 구조가 같고, T7에서도 입 "Ah" 전이는 성공한 반면 눈 감기 피부 전이는 실패했다(내부 문서 `10_T7_표정_스캔`).

여러 연구가 같은 곳에서 막힌다는 사실도 눈에 띈다. IEEE VR 2023 논문은 자동 랜드마크 검출이 사람 얼굴에서는 되지만 스타일 캐릭터에서는 안 된다고 보고했고([IEEE VR 2023](https://fuxivirtualhuman.github.io/pdf/IEEEVR2023_BSGen.pdf)), T2Bs는 VLM으로, OmniFaceRig는 스타일별 파서로 이를 우회했으며, MetaHuman 포럼에는 매끈한 스타일 얼굴에서 얼굴 윤곽 랜드마크 자동 추적이 실패했다는 보고가 있다([UE 포럼](https://forums.unrealengine.com/t/cannot-import-to-custom-mesh-in-metahuman-the-2d-view-shows-only-a-black-head-silhouette/2746663)). **스타일 얼굴의 랜드마크 찾기가 공통 병목**이다. 우리는 MediaPipe 눈 비율이 낮으면 깊이 림으로 바꾸는 규칙으로 character1, f09, f11의 눈꺼풀 고리를 잡아 이 병목을 이미 넘었다(내부 문서 `12_T14_리깅포인트`).

리타게팅 계열은 나중의 구동 단계에서 쓸모가 있다. Ribera 외(SIGGRAPH 2017)는 배우와 캐릭터 리그의 동작 범위를 manifold alignment로 정렬해 희소 대응만으로 스타일 캐릭터에 옮기고([논문](https://cg.cs.tu-dortmund.de/publications/2017-faces.pdf)), Choi 외(CGF 2024)는 과장된 캐릭터에서 로컬 패치 단위 재연이 전역 방식보다 낫다고 보고했다([EG DL](https://diglib.eg.org/handle/10.1111/cgf15263)). 과장된 카툰 얼굴에서 사람의 jawOpen 1.0을 캐릭터의 1.0으로 그대로 옮기면 안 되는 문제가 바로 그 쓰임새다. 마른 얼굴과 뚱뚱한 얼굴은 얼굴 리깅 문헌에서 독립된 축으로 다뤄지지 않으며, 명시적인 사례는 물리 기반 Phace(SIGGRAPH 2017)가 연조직 부피 스케일로 얼굴을 마르게 또는 통통하게 바꾼 데모 하나뿐이다([Phace](https://users.cs.utah.edu/~ladislav/ichim17phace/ichim17phace.html)).

## 문헌과 현장은 어휘 하나, 템플릿 몇 개, 국소는 규칙으로 수렴한다

세 방식을 증거와 나란히 놓으면 셋은 경쟁하는 선택지가 아니라 **층**이며, 성공한 시스템은 모두 셋을 겹쳐 쓴다는 결론이 나온다.

| 방식 | 지지하는 증거 | 반대하는 증거 |
|---|---|---|
| 템플릿 하나 | 구현이 단순하다. QtMeshEditor는 ICT 하나로 사람형을 끝까지 자동화한다 | NFR·NFS가 스타일 메시에서 아티팩트를 내고 스케일에 민감하다. MetaHuman도 강한 스타일화를 경고한다. 과장된 표정은 선형 공간 근사가 나쁘다([Zhang 2020](https://ar5iv.labs.arxiv.org/html/2008.05110)). CC Blink는 2.6 cm 눈을 못 감겼다 |
| 스타일별 템플릿 | OmniFaceRig의 템플릿 3종과 스타일별 파서. hinzka는 애니 샘플을 VRoid에서, 실사 샘플을 FaceCap 모델에서 따로 만들었다. VTuber 쪽은 기본 메시별 템플릿이 표준이다 | 패밀리 밖 얼굴(부리, 곤충)은 여전히 실패한다. 패밀리를 늘릴 때마다 템플릿·라벨·기준을 새로 만들어야 한다 |
| 얼굴마다 재서 규칙 적용 | 랜드마크로 리그를 해부학적 비율에 맞춘 Orvalho 2008([EG DL](https://diglib.eg.org/handle/10.2312/CGF.v27i8pp1997-2012)), NFS의 영역 가중치, Choi 2024의 로컬 패치, Wētā FDLS의 영역 분할([FDLS](https://scribblethink.org/Work/Pdfs/ma_FdlsADeepLearningApproachToProductionQualityControllableAndRetargetableFacialPerformances.pdf)), OmniFaceRig의 눈꺼풀·턱 규칙 | 규칙만으로는 애니가 볼을 쓰지 않는 것 같은 표정의 스타일을 정하지 못한다 |

템플릿 하나가 실패하는 이유는 성격이 다른 두 문제가 섞여 있어서다. 첫째는 기하 크기에 비례해야 하는 양이 템플릿 크기에 묶이는 문제다. 사람 눈 크기로 만든 CC Blink가 2.6 cm 카툰 눈을 못 감겼고, 우리 MPFB eyeBlink 복사도 v3 머리에서 6.2 mm 틈을 남기며 눈꺼풀 정점 42개를 안구 안으로 넣은 반면, 같은 머리에서 계산한 눈 감기는 틈 1.2 mm에 안구 침투 0개였다(내부 문서 `02_얼굴_리그_보고서`). 둘째는 스타일의 움직임 관습이 템플릿에 박혀 있는 문제다. 실사 템플릿의 cheekSquint는 볼을 움직이지만, 셀 셰이딩 애니 얼굴에는 움직일 실제 볼과 코가 없어서 cheekSquint는 아래 눈꺼풀과 입으로, noseSneer는 눈썹으로 옮겨 표현한다([note.com/054](https://note.com/054/n/n60a59495a757)). Perfect Sync라는 이름을 만든 hinzka도 애니 모델은 볼 전체보다 입꼬리나 아래 눈꺼풀 같은 부위를 움직여야 덜 깨진다고 정리했다([hinzka 2021](https://hinzka.hatenablog.com/entry/2021/12/02/005814)). Semantic DT가 말한 기하보다 의미의 문제가 바로 이것으로, 어떤 기하 전이도 noseSneer를 눈썹으로 옮기는 재배정을 스스로 만들어 내지 못한다.

그래서 문헌이 가리키는 답은 층마다 맡을 일을 나누는 것이다. **얼굴 형태에 비례하는 것은 측정 규칙이 맡는다.** 눈 감기 거리, 입술 맞닿음, 턱 피벗, 입꼬리 위치가 여기에 들고, 마른 얼굴과 뚱뚱한 얼굴도 이 층에서 흡수해야 한다. NFS가 학습형 방법의 스케일 취약성을 보고했고 MetaHuman이 극단 비율에서 부피 손실을 경고한 것을 보면, 타깃 자신의 국소 좌표계에서 계산하는 DT와 규칙이 이 축에 더 강하다는 것이 우리의 추론이다. **스타일의 움직임 관습은 스타일별 기증 템플릿이 맡는다.** 애니의 부위 중심 움직임, 카툰의 큰 진폭, 실사의 볼·코 움직임이 여기에 든다. **표정 이름은 ARKit 52 하나로 고정한다.** 연구마다 어휘 크기는 7개(RegHead), 53개(NFR), 96개(RigAnyFace), 최대 155개(OmniFaceRig)로 제각각이고, Wētā는 FACS 퍼펫 리그가 약 900 셰이프까지 불어나는 문제 때문에 근섬유 strain 기반으로 옮겨 갔다([Animatomy](https://dgp.toronto.edu/projects/animatomy), [fxguide](https://www.fxguide.com/?p=287134)). ARKit 52는 기하적 진리가 아니라 **엔진·모캡과 맞물리는 인터페이스**인 셈이다. 따라서 괴물에서 일부 채널을 비우거나 재배정하는 것은 정당한 선택이며, VTuber 도구들도 52개 클립이 존재하기만 하면 비어 있어도 되고 너무 미묘한 셰이프는 건너뛰어도 된다고 안내한다([VSeeFace](https://www.vseeface.icu/), [VMagicMirror](https://malaybaku.github.io/VMagicMirror/en/tips/perfect_sync/)).

스튜디오 관행도 같은 방향을 가리킨다. Disney는 블렌드셰이프가 메모리를 많이 먹고 모델이 바뀔 때마다 민감하게 깨진다고 평가했고([Disney Animation](https://disneyanimation.com/publications/a-deformer-based-approach-to-facial-rigging/)), Epic의 Jeremy Ernst는 카툰풍 마녀 얼굴을 대부분 관절로 구동하고 보정 블렌드셰이프는 약 20개만 썼으며([Jeremy Ernst](https://www.jeremyernst.com/devblog/category/Rigging)), Epic 문서도 실시간 캐릭터 얼굴은 대개 블렌드셰이프만으로 움직이지 않는다고 설명한다([Epic 문서](https://dev.epicgames.com/documentation/unreal-engine/recording-face-animation-on-ios-device-in-unreal-engine)). 크리처 쪽에서 Wētā는 배우에서 유인원으로의 매핑이 결코 직역이 아니라며 FACS를 확장한 크리처 전용 리그를 쓴다([Cartoon Brew](https://www.cartoonbrew.com/vfx/performance-capture-creature-apes-created-war-planet-apes-152357.html)). 뼈로 포즈를 잡고 메시가 바뀔 때마다 자동으로 다시 굽는 우리 구조는 이 관행과 맞고, 사람이 조각한 셰이프 라이브러리를 템플릿에서 정점 단위로 복사하는 방식은 맞지 않는다. 한계도 분명히 해 둔다. 같은 데이터에서 템플릿 하나와 여러 개를 직접 비교한 통제 실험(ablation)이나 일본 애니 스타일 전용 블렌드셰이프 자동 생성 논문은 찾지 못했다. 위 결론은 개별 시스템의 설계 선택과 실패 보고를 엮은 것이지 직접 측정한 결과가 아니다.

## face_auto에 가져올 것은 DT 잔차층, 스타일별 기증 템플릿, 애니 규칙이다

현재 파이프라인은 Blender 헤드리스와 Rigify로 돈다. 원본 머리의 고리를 따라 눈과 입을 자르고, 눈 감기는 눈 양끝(canthus)을 고정하는 규칙으로 계산하며, MPFB 사실형 템플릿 하나에서 표정 포즈 목표를 읽어 Rigify 컨트롤로 풀고 원본 위에 굽는다. 이 구조는 앞 절의 측정 규칙 층과 어휘 층을 이미 갖췄고, 비어 있는 것은 템플릿 움직임을 조밀하게 옮기는 층과 스타일별 기증자다. 아래 표는 조사에서 가져올 수 있는 것을 우선순위대로 정리했다.

| 우선 | 가져올 것 | 근거 | 자원·라이선스 | face_auto 적용 지점 |
|---|---|---|---|---|

1번을 맨 앞에 둔 이유는 지금 남은 핵심 문제, 즉 리그 포인트가 159개인데도 키가 얼굴의 좁은 부분만 뾰족하게 움직이는 문제를 정면으로 겨냥하기 때문이다. 뼈 기반 굽기는 뼈 영향권 밖의 넓은 피부 움직임을 놓치는데, DT는 삼각형별 변형 기울기를 원본 전체에서 최소제곱으로 풀어 그 공백을 메운다. OmniFaceRig가 쓰는 조합(sparse DT 뒤 Delta Mush 다듬기)도 정확히 이것이다. DT는 표정 델타만 풀고 기준 형상은 건드리지 않으므로 neutral은 원본 그대로 남는다. vasiliskatr 코드가 쓰는 numba가 Blender 내장 Python에 설치되는지는 시험되지 않았으니, 이미 있는 별도 venv(landmark-venv)에서 풀고 결과만 bpy로 쓰는 편이 안전하다.

2번은 비용이 가장 적게 들고 f09·f11의 남은 문제와 직접 겹친다. 큰 눈에서는 눈 감기와 eyeWide에 홍채 축소를 넣어 흰자가 보이게 하고 눈을 감을 때 홍채가 튀어나오지 않게 하며, 셀 셰이딩 얼굴에서는 cheekSquint를 아래 눈꺼풀로, noseSneer를 눈썹으로 재배정한다. 좌우 분할은 중앙을 칼같이 자르지 않고 합이 100%가 되는 그라디언트로 나누고, 입 전체를 들어 올리는 경향이 있는 미소 키는 입을 내려 보정하며, funnel과 pucker가 치아를 드러내지 않게 막는다. 선형 셰이프키 때문에 눈꺼풀이 안구를 뚫는 문제는 눈 감기 50% 지점의 보정 키와 드라이버로 막는데, 이는 doc 17에서 열린 과제로 남은 보정 키 런타임 드라이버와 같은 일이다. note.com/054의 정리대로 좌우·상하 대칭을 묶으면 52개는 고유 셰이프 약 30개(그중 입이 15개)로 줄어들므로, 한쪽을 만들고 그라디언트 분할로 미러링하는 구조가 효율적이다.

3번은 사용자가 이미 후속 과제로 정한 스타일별 템플릿에 구체적인 재료를 준다. ICT-FaceKit은 NFR, TopoRig, QtMeshEditor가 공통으로 쓰는 사실상의 연구 표준이므로, MPFB 옆에 두면 기증자 교차 검증과 외부 기준선 비교를 한 번에 할 수 있다. 애니 기증자인 hinzka 데이터는 VRoid 토폴로지 위에 정의되어 있으니, VRoid 머리를 지금의 MPFB처럼 우리 머리에 맞춘 뒤 움직임만 가져오면 된다. 과거에 거부된 VRoid 래핑과 달리 형상은 바꾸지 않는다. 허용 라이선스를 가진 카툰 ARKit 템플릿은 찾지 못했다. ARKit 52개 이상이 들어 있다는 무료 치비 베이스 메시가 있지만([Koban Wanko](https://kobanwanko.gumroad.com/l/ChibiBaseMesh)) 라이선스 확인이 먼저다. 괴물은 당분간 반자동으로 간다. OmniFaceRig처럼 주둥이형 패밀리용 템플릿 1–2개를 손으로 한 번 만들고, ARKit 이름은 의미 채널로 유지하되 맞지 않는 채널은 비우거나 재배정한다. 부리, 곤충, 물고기 입은 어느 시스템도 풀지 못했으니 수작업 대상으로 남긴다.

가져오지 말아야 할 것도 분명하다. 템플릿 래핑 제품(Headshot, MetaHuman, KeenTools)과 FLAME 계열 피팅은 최종 메시를 바꾸고, 몸 오토리거는 얼굴을 만들지 않으며, 이름만 자동 ARKit인 스텁 저장소는 쓸모가 없다. 한편 CaptureForge나 Faceit 같은 GPL 애드온을 우리 파이프라인 안에서 쓰는 것만으로는 산출물인 메시와 셰이프키에 GPL이 붙지 않고, 코드를 재배포할 때만 copyleft가 걸린다. 이는 GPL의 일반적인 해석이지 법률 자문이 아니다.

## Reddit 차단과 미실행 도구라는 두 구멍이 남아 있다

이번 조사에는 세 가지 한계가 있다. 첫째, **Reddit에 접근할 수 없었다.** 웹 검색 도구, 페이지 가져오기, 내장 브라우저 모두에서 reddit.com이 안전 제한으로 차단됐다. 그래서 자기 애니 모델에 특정 도구를 써 본 Reddit 사용자 경험담과 52개 셰이프를 손으로 만드는 데 드는 실제 시간이 보고서에서 빠졌다. Polycount, Fiverr, Etsy 페이지는 HTTP 403을 돌려줘 검색 결과 요약만 썼고, 커뮤니티 증거는 VTuber·VRChat 문서, 일본 블로그, Blender Artists·Unreal·NVIDIA·Reallusion 포럼, Superhive 리뷰, VFX 업계 매체에서 모았다. 둘째, **어떤 도구도 우리 시험 머리 4개(f02, f06, f11, f09)에 직접 돌려 보지 않았다.** 품질 판단은 모두 문서, 논문, 사용자 보고에 근거한다. 셋째, Polywink의 현재 운영 여부, NFR 사전학습 가중치의 상업적 지위, hinzka 데이터의 기반인 VRoid 메시 권리, OmniFaceRig와 RigAnyFace의 코드 공개 일정, Faceit의 헤드리스 공식 지원 여부는 미확인으로 남았다. 애니·카툰·통통한 얼굴·마른 얼굴·크리처별 실패율을 정량화한 자료는 어디에도 없었다.

## 결론

이번 조사로 바뀐 판단은 둘이다. 첫째, 우리가 만드는 것은 기존 도구의 열화판이 아니다. Meta가 2026년에 도달한 설계와 같은 축 위에서 원본 정점을 정확히 지키고 Godot까지 이어지도록 차별화한 구현이다. 상용과 오픈소스가 비워 둔 자리(스타일화·비인간 얼굴, 상업 라이선스, 원본 유지)가 시장 가격이 가장 비싼 지점과 정확히 겹치므로 이 자동화는 발표에서 내세울 근거가 충분하다. 빠진 부품인 조밀 DT와 스타일별 기증 템플릿도 MIT·BSD 구현과 MIT 템플릿으로 모두 구할 수 있어, 남은 일은 새 연구가 아니라 통합이다.

둘째, 템플릿이 몇 개 필요한가라는 질문은 얼굴 형태가 아니라 **움직임 관습**을 기준으로 답해야 한다. 마른 얼굴, 뚱뚱한 얼굴, 큰 눈, 얇은 입술처럼 형태가 다른 것은 측정 규칙과 DT가 흡수할 몫이지 템플릿을 늘릴 이유가 아니다. 템플릿은 실사, 애니, 카툰, 주둥이형 크리처처럼 표정을 어떻게 움직이는지가 다를 때만 늘린다. 이 기준이면 기증 템플릿은 4–5개에서 상한이 생기고, 새 캐릭터마다 드는 비용은 측정과 규칙으로 옮겨 간다. 앞으로 지켜볼 것은 OmniFaceRig·RigAnyFace의 코드 공개와 TopoRig의 라이선스 변경이며, 하나라도 풀리면 우리 4개 머리에서 바로 비교해 볼 가치가 있다.

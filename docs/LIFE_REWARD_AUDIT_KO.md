# 마을 생활 보상 서버 권위 감사

감사일: 2026-10-16. 대상: `codex/lifeauth`의 생활 보상 API와 보상에 연결된 원정·운영 경로. 시작 시 기존 코드 변경은 없었고 `CODEX_TASK.md`만 추적되지 않은 상태였다. `game/`, `server/multiplayer.py`는 수정하지 않았다. 커밋·푸시·배포·외부 서비스 호출은 하지 않았다.

## 결과와 공통 보장

보상 금액·아이템 수량의 직접 주입과 같은 요청의 재전송으로 무제한 지급되는 경로는 확인되지 않았다. 시간대 헤더로 보상 조건을 바꾸는 문제, 반복 NPC 선물에 친밀도 일일 상한이 없는 문제, 금액 필드의 자동 형 변환, 잎전 잔액의 명시적 정수 범위 검증 부재를 수정했다. **실제 방문·거리·낚시 미니게임 성공까지 서버가 증명하는 상태는 아니다.** 이를 해결하려면 아래의 클라이언트/이동 계약 변경이 필요하다.

- 아래 표의 **요청 멱등성**은 인증된 사용자와 `request_id`를 키로 `operation` 및 본문 fingerprint를 비교하고, 같은 요청에는 저장된 응답을 반환하는 `app.mutate`를 뜻한다. 다른 본문이나 다른 대상/작업으로 같은 ID를 쓰면 `409 request_id_reused`다.
- `BEGIN IMMEDIATE` 트랜잭션 안에서 보상, 아이템 소비, 완료 기록, 요청 응답이 함께 확정된다. 실패하면 이 변경들은 롤백된다. `EconomyRejected` 보안 탐지 기록은 별도 트랜잭션으로 보존한다. `request_id`를 새로 만들어도 객체·완료 상태·버전·원장 제한은 우회되지 않는다.
- 별씨는 `economy.change_shards`만 변경한다. `ledger`의 사용자·사유·reference 유일성, 정수 검사, 음수 잔액/64비트 범위 초과 방지가 있다. 생활·관리자 HTTP 경로의 잎전 변경도 이번에 `economy.change_coins`로 통합했다. 잎전은 별도 원장이 아니라 homestead JSON에 저장되며 같은 DB 트랜잭션과 버전으로 보호한다. 기존 운영 계정 초기화 스크립트 `tools/admin_accounts.py`의 잎전 최소잔액 설정은 이번 수정 범위에 포함하지 않았다.
- 생활 보상의 밤 조건과 일일 상한은 계정 최초 인증 때 저장된 `users.daily_utc_offset`을 사용한다. 헤더 변경이나 재로그인·서버 재시작으로 다시 선택할 수 없다. 최초 선택 자체를 신뢰하는 한계는 남는다. 관리자 별씨 지급·공개 가입·상호작용 생성의 일일 제한은 UTC 기준이다.
- 본문 모델은 정의되지 않은 필드를 거절한다. `amount`, `rarity`, `stars`, `fish_id`, `owner_id` 등을 임의로 넣어 보상을 지정할 수 없다. 전역 일반 요청 제한은 계정당 분당 1,200회지만 아래 개별 제한을 대체하지 않는다.

| 운영 지급: `POST /v1/admin/grant` | 인증된 admin만 지정, 필드당 정수 0~100000 | 요청 멱등성 + 권한 + 별씨 원장, 잎전과 같은 트랜잭션 | 별씨 UTC일 200000; 잎전은 호출별 제한 및 잔액 범위 | 잎전 정수·잔액 검사 수정; 일반 사용자 접근 불가 |
| 데모 준비: `admin_cli demo prep` (`server/demo.py`) | 운영 CLI가 0~10000 목표 잔액 설정, 선택한 물건 복제 | HTTP 경로 없음; 별씨는 목표 잔액과의 부족분만 원장에 반영 | 같은 잔액에서 다시 실행하면 별씨 추가 0; 소비 후 보충/물건 재복제/reset 가능 | 운영 권한으로 의도된 반복 작업; 플레이어 보상 API가 아님 |

`catalog.py`는 원정 맵·난이도·보상 배율의 서버 자료다. 생활 판매표는 `homestead.PRICES`이며 시장 가격과 구별된다. 주민 퀘스트는 총 19개, 기본 보상 합계 82별이다. 서버 scale은 0~5이고 제작 퀘스트 보상은 개별 최대 20별로 제한된다. 상자는 하루마다 재생성되는 구조가 아니라 계정 평생 1회다.

## 반영한 수정과 검증 근거

1. **시간대에 따른 보상 우회**: `homestead.reward_night`가 고정 계정 시간대로 어종과 야간 퀘스트 수락/진행을 판정한다. 표시용 `night`는 기존 기기 시간대 동작을 유지한다. 헤더만 바꾼 낮에는 밤 어종·방문 진척을 얻을 수 없고, 실제 계정 밤에는 낮 헤더에도 정상 처리되는 회귀 검증을 추가했다.
2. **반복 NPC 선물**: 영구 `npc_gifts` 기록을 계정·NPC·해당 날짜로 합산해 30점까지만 지급한다. 상한 도달 시 `429 npc_gift_daily_limit`이며 물건 소비 전에 거절한다. 조회/성공 응답에 `daily_gain={earned,cap,remaining}`을 추가했다. `can_gift`는 구형 클라이언트 호환을 위해 기존의 “자기 마을인가” 의미를 유지한다. 동시 요청도 직렬 트랜잭션 안에서 같은 기록을 검사한다.
3. **금액 입력**: `LifeAction.quantity`, `Listing.price`, `AdminGrant.coins`를 strict 정수로 제한했다. 이미 strict였던 `AdminGrant.shards`도 함께 검증했다. bool, 숫자 문자열, `1.0` 같은 float, 음수, 과대 정수, NaN/Infinity를 거절한다. 거절된 요청은 가방·잔액·목록·원장·요청 기록을 바꾸지 않는다.
4. **잎전 정수/범위**: 구매·판매·배달·관리자 지급의 잎전 변경을 `economy.change_coins`로 모았다. 변경량은 signed 64비트 정수, 잔액은 0~`2**63-1` 정수여야 한다. 잘못된 잔액/범위 초과는 409이며 판매 아이템 소비, 관리자 별씨 지급, 감사 이벤트까지 롤백됨을 HTTP 테스트로 확인했다. 초기 상태의 잎전 12는 상태 초기화 값이다.
5. **기존 방어 회귀 검증**: 상자 보상 필드 주입, 같은 상자 경쟁 개봉, 날짜를 넘긴 전체 상자 재개봉, 요청 재사용, 원장 일치, 별씨/잎전 경계값 검증을 보강했다. 상자 설명의 오래된 개수/총액도 실제 12개/48별로 맞췄다.
6. **로컬 게임 테스트 도구 호환**: `tools/life_bridge.py`도 `CoinRejected`를 기존 생활 거절 오류처럼 반환하도록 맞췄다. 잔액 부족이 `invalid_request`로 바뀌지 않고 `life_not_enough_coins`를 유지하며, 거절 시 상태 파일을 변경하지 않는지 추가 검증했다.

## 클라이언트가 반영해야 할 계약

### 이번 서버 변경과 연결되는 항목

- `POST /v1/homestead.quantity`는 JSON 정수 1~20, `POST /v1/market.price`는 JSON 정수 1~10000, `/v1/admin/grant.coins`와 `shards`는 JSON 정수 0~100000을 보내야 한다. `true`, `"1"`, `1.0`은 `422 invalid_request`다. `game/`은 변경하지 않았다.
- `game/scripts/npc_gifts.gd`의 선물 화면 시작 처리에서 `GET /v1/npcs/{id}/gift`의 `daily_gain.remaining==0`이면 “오늘 받을 수 있는 친밀도를 모두 받았습니다”를 표시하고 제출을 막아야 한다. 기존 `can_gift=false`의 “본인 마을에서만 가능” 안내는 유지한다. 오류 문구 처리에 `npc_gift_daily_limit`을 추가하고, 429이면 아이템이 소비되지 않은 것으로 처리하며 무한 자동 재시도를 중단한다. 성공 시 친밀도 증가는 반드시 응답 `gain`을 사용한다(상한 직전에는 1점일 수도 있다). 네트워크 재시도는 같은 `request_id`와 같은 본문을 유지한다.
- 기기 시간대에 따른 `/v1/homestead`의 `night` 응답은 보상 판정과 다를 수 있다. 클라이언트가 이를 이용해 야간 퀘스트 진척이나 어종을 확정하면 안 된다. 서버 응답과 `quest_not_night`를 처리해야 한다. 후속으로 `reward_utc_offset/reward_night` 조회 필드를 추가한 뒤 `game/scripts/village_life.gd`의 어종 안내와 `game/scripts/quests.gd`의 `night_now()` 및 실내/야외 방문 보고 전 야간 검사를 그 값으로 바꿔야 한다. **이 두 조회 필드는 이번 구현에 없다.** 로컬 시각만으로 보고를 막으면 기기 시간대 변경·서머타임 적용 후에는 정상 야간 행동도 누락될 수 있다.
- 잎전 변경의 `409 invalid_coin_amount`, `invalid_coin_balance`, `coin_balance_overflow`에서는 성공 연출이나 아이템 소비를 확정하지 말고 서버 상태를 다시 조회한다. 요청을 새 ID로 무한 재전송하지 않는다.

### 거리·성공 증명에 필요한 후속 계약: 이번에는 구현하지 않음

현재 마을 이동은 로컬 처리이고 `/v1/social/presence` 좌표·장면도 클라이언트 보고다. 이 좌표만 보상 API에 추가하거나 비교하면 순간이동 위조는 그대로 남는다. 안전한 전환에는 다음을 함께 적용해야 한다.

1. 서버가 마을 위치, scene/place/floor, 이동 순번을 확정한다. 클라이언트는 이동 결과 좌표 대신 `{sequence, dx, dz, sprint}` 의도를 전송하고, 서버는 시간·이동속도·장면 전환을 검사한 위치와 `accepted_sequence`를 응답한다. 기존 presence와 분리한 이동 경로 또는 그와 동등한 서버 검증이 필요하다.
2. 보상 요청에 `{request_id, position_sequence}`를 추가해 서버가 수락한 위치를 참조하게 한다. 생활 요청은 기존 `version/action/node/plot/spot/item/quantity`도 유지한다. 서버는 최신 순번·본인 마을·장면과 대상 거리 모두를 보상과 같은 트랜잭션에서 검증한다. 타인 마을 허용 여부를 행동별로 명시해야 한다.
3. 상자·채집·나무·밭·수역·NPC의 실제 상호작용 좌표와 장면을 서버 자료로 제공한다. 클라이언트는 그 배치를 사용해야 한다. 특히 상자는 현재 클라이언트가 후보 위치나 주변 보정으로 배치하므로, 서버 좌표와 일치시키고 개봉 거리 1.65m 기준을 같은 값으로 사용해야 한다. 다른 대상의 반경도 서버 명세와 UI를 맞춘다.
4. `quests/.../progress`의 `place`, **`quests/.../accept`의 즉시 방문 인정용 `place`**, `story/step`의 인사 보고를 모두 서버가 검증한 방문/대화 이벤트에 연결한다. accept에서 이를 검증하지 않을 경우 그 경로의 자동 방문 진척을 제거해야 한다. 요청마다 새로 만들어낼 수 있는 클라이언트 토큰은 증거가 아니다. 이벤트는 사용자·대상·상호작용·유효기간에 묶어 서버가 발급/소비해야 한다.
5. 낚시 `outcome=landed`만으로 미니게임 성공을 결정하는 계약을 바꾼다. 서버 발급 낚시 세션 ID와 순번 있는 reel 입력을 보내고, 서버가 시간 경과·장력·진척·성공을 판정해 결과를 반환한다. 지금의 입질/싸움 최소시간은 속도 제한이지 성공 증명은 아니다.
6. 구형 `gather,item=apple/herb`는 노드가 없으므로 이동 계약 전환 시 클라이언트를 정식 `node` 기반으로 옮기고, 지원 버전 전환 후 구형 경로를 종료해야 한다. 이번에는 기존 쿨다운을 유지했다.

## 남은 위험과 범위

- 거리/방문/대화/낚시 성공 보고를 위조하는 스크립트는 현재의 품목·쿨다운·일일/계정 상한 안에서 보상을 받을 수 있다. 현재 클라이언트를 깨뜨리는 불완전한 위치 검증을 넣는 대신 위 후속 계약을 명시했다.
- 농사·채집·낚시·일반 원정·튜토리얼은 반복 플레이 구조다. 서버 시간이 필요한 만큼 HTTP 연타만으로 무제한 즉시 지급되지는 않지만 장기간 자동화는 가능하다. 판매 별씨 하루 15 제한이 원정 별씨까지 제한하지는 않는다. 원정 전체 발행량 상한은 싱글/협동을 함께 다루는 별도 정책·구현이 필요하다.
- 계정별 제한은 다계정 합산을 막지 못한다. live 공개 가입에는 기존 IP/전체 일일 제한이 있지만 초대 코드를 가진 가입 및 demo 계정에는 같은 일일 가입 제한이 적용되지 않는다. 초기 보상과 유한 퀘스트·상자 별씨를 시장 거래로 옮기는 행위는 계정 단위 제한 밖이다. demo는 로컬 접근만 허용한다.
- 친밀도/퀘스트의 물건 분류 일부는 이름·설계 태그·버전에 의존한다. 보상량은 서버가 고정하지만 의도한 물건 의미나 실제 외형 변화까지 강제하지는 않는다. 서버가 서명한 품목 분류·실제 속성 비교가 필요한 후속 항목이다.
- 고정 계정 시간대의 최초 선택, 운영자의 story reset·demo 복제/보충, 관리자 지급은 별도 신뢰 경계다. 운영자의 명시적 리셋으로 생긴 재보상은 플레이어 요청 재전송과 구별한다.

& 'C:\lsm26\triphthonS1\.tools\server-venv\Scripts\python.exe' -m pytest server/tests -q

# PERF_0118 데모 서버 폴링 성능 점검

측정일: 2026-10-16. 기준 커밋: `e9ad0065398ff65a5efeb3f46d250023695b3a8c` (`codex/perf`).

60명이 1초마다 presence를 보내면서 채팅·집·NPC 집·제작 상태를 함께 조회할 때, presence p95는 **20.046 → 8.074ms**로 59.7% 줄었다. 전체 요청 p95는 **15.529 → 7.336ms**이며 모든 측정에서 HTTP 오류와 예외는 0건이었다. 대기 없는 포화 부하에서는 처리량과 꼬리 지연이 개선되지 않았다. 이 결과를 VM의 최대 수용 인원으로 해석하면 안 된다.

## 측정 조건과 재현

- Windows 10 로컬 PC, 논리 CPU 24개, Python 3.13.14, SQLite 3.50.4. 네트워크·TLS·프록시를 제외한 FastAPI TestClient를 사용했다. 서버 프로세스나 리스닝 포트를 띄우지 않았다.
- 각 조건은 별도의 임시 SQLite DB, 워밍업 3초 + 본 측정 30초. 변경 전 3개 조건을 먼저 측정하고 코드를 수정한 뒤 같은 조건을 순서대로 측정했다. 성능 측정 중 pytest는 실행하지 않았다. 다른 프로세스의 부하나 CPU 배치를 통제하지 않았다. 조건별 1회 측정이므로 통계적 신뢰 구간은 제시하지 않는다.
- 현재 사용자 30/60명에 누적 비접속 계정 300명을 더했다. 계정마다 가구 24개(마을 12개, 집 12개), 총 7,920/8,640개. 모두 합성 자료이며 기존 DB를 열지 않는다.
- 3명씩 파티·호스트/방문자 그룹을 만들고, 절반은 집 안·절반은 마을에 배치했다. 각 활성 사용자에게 작물과 제작 중인 작업 1개를 준비했다. 정상 로그인 과정을 측정하는 대신 합성 세션을 직접 넣어 가입 제한·암호 해싱을 제외했다.
- 사용자별 presence는 지정 간격, 제작 상태는 약 3초, `/v1/me`와 NPC 집 조회는 약 5초, 지역 채팅은 약 10초 간격이다. 부가 조회는 다음 presence 주기에 실행되므로 실제 횟수는 조금 달라질 수 있다. 채팅 커서는 응답에 따라 전진한다.
- 한 TestClient의 단일 앱/이벤트 루프를 공유하고 사용자마다 스레드 1개를 사용했다. 정상 부하는 시작 시점을 분산한다. 사용자당 요청은 직렬이며 늦은 주기를 무한히 쌓거나 몰아서 재전송하지 않는다.
- `--interval 0`은 서버의 폴링 간격 권고를 무시하는 closed-loop 포화 실험이다. 이는 1~3초 폴링 목표 부하와 구분한다. 지연은 요청 호출부터 응답 완료까지이고, 초당 요청 수는 워밍업을 제외한 실제 경과 시간(마지막 요청 완료 대기 포함)으로 계산한다. p50/p95는 nearest-rank다.
- 앱 백그라운드 제작 워커는 껐다. 제작 **상태 조회**를 측정하며 생성·파일 다운로드 비용은 포함하지 않는다. 환경의 서비스 설정/키를 제거하고 HTTPX 실제 네트워크 전송을 차단한다. 토큰·비밀번호·응답 본문은 보고서에 저장하지 않는다.

```powershell
$python = "C:\lsm26\triphthonS1\.tools\server-venv\Scripts\python.exe"
& $python tools/bench_presence.py --players 30 --interval 3 --seconds 30 --label after --output docs/perf_0118/after-30p-3s.json
& $python tools/bench_presence.py --players 60 --interval 1 --seconds 30 --label after --output docs/perf_0118/after-60p-1s.json
```

변경 전 재현에는 위 기준 커밋의 서버와 동일한 `tools/bench_presence.py`를 사용한다. `--history-users 0`으로 빈 서버도 비교할 수 있다. 기본 가구 수는 `--objects 24`다. 임시 DB는 작업 폴더의 `.tools/bench-presence/` 아래에서 만들고 연결을 닫은 후 제거한다. 출력 경로는 작업 폴더 내부로 제한한다. 오류가 있으면 도구는 0이 아닌 종료 코드를 반환한다.

## 확인한 병목과 변경

### 인덱스 마이그레이션

`server/migrations.py`를 추가하고 모든 기능 테이블 생성 후 `create_app`에서 실행한다. 세 인덱스와 `metadata`의 `migration:0118_polling_indexes` 표식을 한 트랜잭션에 저장한다. 기존 DB에도 적용되며 실패하면 표식과 인덱스를 함께 롤백한다.

| 인덱스 | 해결하는 조회 |
|---|---|
| `objects_owner_state_id(owner_id,state,id)` | 호스트의 배치된 가구 조회와 ID 순서 정렬; 전체 사용자 가구 스캔 제거 |
| `mp_visits_host_expires(host_id,expires,user_id)` | 호스트의 방문자 정리·수용 인원·방문자 목록 |
| `mp_presence_host_scene_seen(host_id,scene,seen)` | 호스트·장면·최신 접속 시간으로 현재 플레이어 조회 |

동일한 간소화 가구 쿼리의 `EXPLAIN QUERY PLAN`은 `SCAN objects USING INDEX sqlite_autoindex_objects_1`에서 `SEARCH objects USING COVERING INDEX objects_owner_state_id (owner_id=? AND state=?)`로 바뀌었다. 실제 가구 응답은 추가 열과 조인을 읽으므로 전체 쿼리가 covering scan이라는 뜻은 아니다. 테스트는 세 조회가 각 인덱스를 사용하는지 확인한다.

### 쓰기 잠금과 N+1

- `/v1/studio/jobs/{job_id}`와 `/v1/generations/{job_id}`를 `db.transaction()`에서 `db.read()`로 변경했다. 기존 인증·소유권 조건은 유지한다. 제작 상태 조회 SQL 추적에서 `BEGIN IMMEDIATE`가 1 → 0회가 됐다.
- 파티원 3명의 `seen`을 각각 조회하던 루프를 멤버 조회의 `LEFT JOIN mp_presence`로 합쳤다. 정렬, 응답 키, 미접속/만료 판정은 그대로다. 플레이어 아바타 조회는 최대 3명 규모의 N+1이 남아 있고 이번 범위에서는 유지했다.
- 진단용 단일 presence 요청의 SELECT 수는 집 장면 기준 대략 37 → 33회다. roster 갱신 타이밍에 따라 1회 차이가 난다. 3회는 파티원 조회 통합, 1회는 집 장면에서 필요 없는 homestead 조회 제거다.

### JSON 처리와 캐시 무효화

- 기존 presence는 이미 `JSONResponse`를 직접 반환해 FastAPI의 일반 인코더 순회를 피하고 있었다. JSON 최종 인코딩은 유지한다. `village`와 `space`가 같은 마을 정보를 중복 포함하는 기존 계약도 유지한다.
- `homestead.public_crops(raw, now)`는 전체 개인 생활 상태·카탈로그를 깊은 복사하는 대신 방문자에게 필요한 버전과 밭만 만든다. 집 장면에서는 작물 데이터를 생성하지 않는다.
- 저장된 JSON 문자열 전체를 키로 하는 LRU 캐시(최대 128개)를 사용한다. 매 요청 DB를 읽으므로 저장 변경, 복원, 버전 번호를 유지한 수정도 즉시 다른 키가 된다. TTL 때문에 이전 결과가 남아 보이는 구간은 없다. 롤백된 쓰기는 다음 요청의 키가 되지 않는다.
- 65,536자를 넘는 저장 내용은 캐시를 우회한다. 캐시 키에는 원본 문자열이 있으므로 개인 데이터가 프로세스 메모리에 일시 보관될 수 있으나 응답에는 포함하지 않는다. 한도는 바이트가 아닌 문자 수이며 파이썬 객체 오버헤드도 있다.
- 반환하는 밭은 매번 복사하고 성장 완료 여부·남은 시간·서버 시간은 매번 계산한다. 세션·방문 권한·잔액·전체 응답은 캐시하지 않는다. 새 저장 내용의 이전 캐시 항목은 LRU 퇴출 시 제거된다.

### WAL, 디스크 쓰기, 연결 풀

기존 `server/database.py`는 WAL, `busy_timeout=15000`, 유휴 연결 풀 8개, `journal_size_limit=16777216`을 이미 사용한다. 일반 거래는 `synchronous=FULL`, presence의 재생성 가능한 위치 쓰기만 `NORMAL`을 사용하며 커밋 직후 writer를 놓고 읽기 스냅샷으로 전환한다. 이 설정과 내구성 동작은 변경하지 않았다.

presence는 여전히 매 요청 위치 UPSERT, 방문자 만료 갱신, 필요 시 NPC 이동을 기록한다. 채팅도 쓰기 트랜잭션과 보존 기간 정리가 필요하다. 채팅 정리의 큰 삭제량, 신규 계정의 최초 timezone 기록, 첫 인덱스 생성, 제작 워커의 파일/DB 작업은 경합을 늘릴 수 있다. 이번 변경으로 디스크 쓰기가 사라진 것은 아니다. 유휴 풀 크기는 동시 연결 수 상한이 아니므로 이를 키워 writer 경합이 해결된다고 가정하면 안 된다.

## 통합 세션 검토: multiplayer.py 최소 변경

`server/multiplayer.py`의 변경은 **두 구간, 8줄 추가·8줄 삭제**뿐이다.

1. `party_public`: 멤버 쿼리에 `LEFT JOIN mp_presence`를 추가하고, 내부 `seen`을 응답에서 제거한 뒤 기존 기준으로 `online`을 계산한다.
2. `village`: 마을에서만 `homestead.public_crops`를 호출하고 집에서는 `crops=None`을 그대로 반환한다.

presence 요청 모델, 위치 쓰기, 방문 만료, 권한 검사, 채팅 커서, 응답 최상위 필드, 쓰기/읽기 트랜잭션 경계는 수정하지 않았다. 통합 세션은 이 두 구간과 `homestead.public_crops` 의존성을 함께 검토하면 된다.

## 검증과 진행 기록

- 시작 시 기존 미커밋 코드 변경은 없었고 `CODEX_TASK.md`만 추적되지 않은 상태였다.
- 잘못된 sparse 경로로 서버 파일이 비어 있어 현재 커밋의 서버·도구·문서·운영 설정과 테스트에 필요한 게임 자료를 작업 폴더에 복원했다. Git 메타데이터를 바꾸지 않았고 복원 자료 자체의 내용 변경도 없다.
- 변경 전 전체 테스트: **1,126개 통과**. 첫 실행은 기존 시스템 임시 폴더 접근 제한으로 fixture 생성이 실패하여, 이후 TEMP/TMP를 작업 폴더 내부로 지정했다.
- 추가 성능 회귀 테스트: **11개 통과**. 기존 DB 업그레이드·실패 롤백·쿼리 계획, 다른 writer가 열린 동안의 제작 상태 조회·인증·소유권·로그아웃, 이전 저장 형식과 작물 계약 일치, 캐시 한도·큰 저장 우회·시간 경과·변경·롤백·호스트 전환, 파티원의 미접속·만료, presence 오류 후 FULL 복원 등을 확인한다.
- 변경 후 첫 전체 검사: 1,136개 통과, 계정 생성의 Argon2 메모리 할당 오류 1건. 해당 테스트는 단독 재실행에서 통과했다. 인증 비용이나 테스트 조건을 낮추지 않고 전체를 재실행했다.
- **최종 전체 검사: 1,137개 통과, 경고 1개, 683.07초.** 지정된 `python -m pytest server/tests -q` 명령이 종료 코드 0으로 완료됐다. 추가 테스트 11개를 포함한다. `git diff --check`도 통과했다.

## 작은 VM 운영 권고와 남은 위험

다음은 저장소 설정과 이번 로컬 결과에 근거한 시작점이며 실제 VM 검증 결과가 아니다.

- `ops/compose.yaml`의 **uvicorn worker 1개**를 유지한다. 현재 roster·rate limit·poll meter는 프로세스 메모리를 사용한다. 여러 worker로 늘리면 SQLite 경합과 각 프로세스 상태 불일치가 생길 수 있다.
- 시작 구성은 2 vCPU와 RAM 2~4GiB, 로컬 SSD 계열 영구 디스크로 잡고 관찰한다. 기존 컨테이너 메모리 상한은 2GiB이므로 호스트가 2GiB라면 프록시·OS 몫까지 같은 한도를 소모하지 않도록 조정해야 한다. 버스트형 VM은 CPU 크레딧과 I/O 지연을 함께 본다.
- 30~60명 데모는 `VILLAGEN_PRESENCE_TOGETHER=1`, `VILLAGEN_PRESENCE_ALONE=3`, `VILLAGEN_PEOPLE_SECONDS=5`, `VILLAGEN_PRESENCE_BUDGET=60`을 초기 권고로 삼는다. 설정 변수는 현재 compose/config에 이미 있다. 클라이언트가 서버 권고를 실제로 따르는지 확인해야 하며 기존 0.25초 고정 폴링 클라이언트에는 이 측정의 여유를 그대로 적용할 수 없다.
- WAL과 15초 busy timeout을 유지하되 이를 응답시간 보장으로 보지 않는다. `synchronous=OFF`, 모든 거래의 `NORMAL` 전환, 요청마다 강제 checkpoint/VACUUM은 권고하지 않는다. 인덱스 최초 생성은 요청을 받기 전 실행되므로 큰 DB에서는 시작 시간이 늘 수 있다.
- 예시 점검 기준은 목표 부하에서 presence p95 100ms 이내, 오류/`database is locked` 0건이다. 이번 PC는 이 기준을 만족했지만 VM에서는 별도 확인해야 한다. p95/p99·최댓값, CPU·RSS, WAL 크기, 저장소 지연과 실제 폴링 횟수를 같이 관찰한다.
- 이번 30초 측정은 장시간 누적 채팅·보존 정리·큰 NPC 배치 변경·백업·유료 제작/다운로드·로그인 폭주·네트워크 비용을 검증하지 않았다. 특히 포화 실험의 최악 12.23초는 남은 위험이다. 한계 부하 개선이 필요하면 SQLite writer 대기/공정성부터 별도로 계측하고 요청 제한 또는 쓰기 직렬화 방식을 검증해야 한다.
- `mp_presence` 복합 인덱스는 조회를 줄이는 대신 위치 갱신 때 인덱스 쓰기를 추가한다. 객체/방문 인덱스도 저장 공간과 변경 비용이 있다. 작물 캐시가 자주 바뀌거나 큰 저장으로 우회되면 캐시 이익은 작아진다. 운영 데이터 규모에 따라 다시 측정한다.

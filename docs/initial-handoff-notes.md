# Tripothon Godot 프로토타입

2026년 9월 30일에 빈 폴더에서 시작한 Godot 3D 게임입니다. 첨부된 Unity 제작계획서는 이전 검토 자료이며 현재 구현의 기준은 사용자의 새 방향입니다.

## 현재 방향

평화로운 마을 탐색 → 별도 공간에서 게임 시간 7일 생존 → 성과 보상 → 보상 재화로 Tripo 3D 오브젝트 생성 → 직접 색칠 → 마을 장식으로 이어집니다. 생존은 돈스타브의 채집·제작·밤 생존을 출발점으로 삼고, 마인크래프트의 직접 조작·배치 감각을 참고합니다. 블록 지형이나 복셀 월드 제작까지 확정한 것은 아닙니다.

7일은 게임 내 시간으로 가정했습니다. 하루 길이, 사망 시 보상, 전투 비중은 아직 미정입니다. 오브젝트 거래와 다른 지원 서비스 활용은 후속 확장 후보입니다.

## 첫 작업 구현 상태

- 실제 실행 버전: Godot `4.7.2.stable.official.ed1daf0bf`, GDScript, Compatibility 렌더러.
- 작은 3D 마을, 캐릭터 이동, 따라오는 직교 카메라, 바닥·건물·물체 충돌.
- 자체 제작한 무채색 의자 GLB를 게임 실행 중 읽고 크기와 바닥 위치를 정규화.
- 개별 인스턴스에 전체 단색 적용, 바닥 배치, 90도 회전, 마지막 배치 회수.
- 물체 겹침·플레이어 위·마을 밖 배치 방지, 최대 30개.

샘플 모드는 실제 AI 생성이 아닙니다. API 키 입력·네트워크 요청·과금은 없습니다. 현재 색칠은 머티리얼 단색 변경이며 붓/면 색칠은 없습니다. 물체는 장식과 충돌만 지원합니다. 의자에 앉기, 저장, 생존, 보상, 서버, 실제 Tripo 연동, 거래, 배포 빌드는 아직 구현하지 않았습니다.

## 실행

프로젝트 폴더에서 PowerShell로 실행합니다.

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\run_game.ps1
```

Godot 에디터로 열려면 다음을 실행한 뒤 F6 또는 F5를 누릅니다.

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\run_game.ps1 -Editor
```

직접 Godot에서 `game/project.godot`를 가져와 F5로 실행해도 됩니다. 공식 포터블 엔진은 로컬 `.tools/godot/`에 있고 Git 추적 대상에서 제외했습니다. 다른 PC에서는 Godot 4.7.2 일반판을 준비해야 합니다.

WASD/방향키로 이동합니다. ‘샘플 의자 불러오기’를 누르고 색을 선택한 다음 마을 바닥을 클릭합니다. 배치 중 이동은 잠깐 멈춥니다. R은 회전, Esc는 취소, Backspace는 마지막 물체 회수입니다. 종료하면 배치는 초기화됩니다.

## 첫 작업 완료 기준과 검사

1. 마을이 실행되고 캐릭터가 바닥에 서서 움직인다.
2. 의자가 무채색으로 로드되고 선택한 색을 표시한다.
3. 서로 다른 색의 의자 두 개가 서로의 색을 바꾸지 않는다.
4. 의자를 놓고 걸어가면 충돌하며, 같은 자리에 중복 배치할 수 없다.

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\run_game.ps1 -Check
```

`game/tests/smoke.gd`는 실제 Godot 런타임으로 GLB 5개 파츠의 로드, 크기·바닥 정렬, 색 독립성, 이동·충돌, 잘못된 배치 거부를 검사합니다. Windows 배포본과 다른 PC의 실행 여부는 별도 검증 대상입니다.

## 다음 작업 순서

한 단계씩 동작을 확인하고 다음으로 넘어갑니다.

1. **생존 한 판:** 채집 대상, 식량·허기·체력, 낮과 밤, 게임 시간 7일, 성공/실패, 마을 복귀. 예상 새 파일은 `survival_run.gd`, `survival.tscn`입니다. 완료 기준은 입장부터 결과까지 한 판 완주입니다.
2. **서버와 재화:** 계정/세션, 도전 결과 검증, 보상 원장, 생성 요청·상태·중복 방지. 서버 언어와 호스팅은 아직 고정하지 않았습니다. 완료 기준은 같은 완료/생성 요청을 반복해도 보상·차감이 한 번만 일어나는 것입니다.
3. **실제 Tripo 연결:** 서버에만 키를 저장하고, 생성 결과를 보관해 Godot으로 전달합니다. 계정 진단 성공과 실제 GLB 수신을 별도로 확인합니다. 완료 기준은 텍스트 → 실제 GLB → 색칠 → 배치입니다.
4. **저장과 제출:** 모델·색·배치 저장, 실패 시 샘플 대체, Windows 배포 검사, 녹화와 제출 자료를 준비합니다.

## 서버 설계 기준

Godot 클라이언트 → 게임 서버 → Tripo 순으로 요청합니다. 게임 서버는 Tripo 키를 보관하고 클라이언트에는 세션 토큰과 생성 작업 상태·모델 파일만 전달합니다. 키를 내려주는 엔드포인트는 만들지 않습니다.

사용자에게는 이름과 아이콘이 있는 생성 재화를 표시합니다. 서버에서는 플레이어 재화 원장과 실제 Tripo 크레딧을 분리하고 생성할 때 연결합니다. 생존 보상은 Tripo 계정 잔액을 늘리지 않습니다. 실제 단가를 확인한 뒤 재화 소모량과 전체 생성 상한을 정해야 합니다. 공급자 잔액만큼만 생성할 수 있으며, 생성 요청 예약·성공 정산·실패 처리를 구분합니다.

실제 생성 비용이 연결되므로 클라이언트가 보낸 점수를 그대로 믿고 재화를 지급하지 않습니다. 도전 ID, 서버가 검증 가능한 결과 규칙, 중복 수령 방지가 필요합니다. 거래를 추가한다면 물체 소유권과 재화 이전을 서버에서 함께 처리합니다. 현재 로컬 프로토타입 결과는 실제 생성권을 발급하지 않습니다.

### 확정된 접근 및 소유권 검증 요구사항

사용자는 접근 권한과 소유권을 매우 엄격하게 검증할 것을 요구했습니다. 아래는 서버 구현의 필수 요구사항이며, 현재 로컬 프로토타입에 구현되거나 보안 검증을 통과한 기능이 아닙니다. 거래 방식(개별 물건 양도 또는 디자인 복수 판매)은 아직 미정입니다.

- **서버가 최종 판단합니다.** 계정, 소유권, 수량, 재화, 가격, 보상, 거래 상태는 서버의 기록을 기준으로 합니다. 클라이언트가 보낸 사용자 ID·소유자·잔액·점수나 로컬 세이브를 권한의 증거로 사용하지 않습니다. 행위자는 서버가 검증한 세션에서 결정합니다.
- **기본은 거부입니다.** 목록·개별 조회·파일 전송·색 수정·배치·판매 등록·구매·취소·생성 작업 조회 등 모든 보호 대상 요청에 행위별 권한 검사를 적용합니다. 화면에서 버튼을 숨기는 것으로 검사를 대신하지 않습니다. 목록·일괄 처리에도 항목별 권한 조건을 적용합니다.
- **모델과 소유 물건을 구분합니다.** 파일을 식별하는 assetId와 서버가 발급한 소유 개체 instanceId를 분리합니다. GLB·파일 해시·ID를 알고 있거나 복사했다고 소유 개체가 발급되지 않습니다. 외부 파일 업로드로 임의의 거래 물건을 등록하는 경로는 초기 거래 기능에 포함하지 않습니다.
- **행위에 필요한 상태까지 검사합니다.** 소유권 외에도 대상 마을의 편집 권한, 판매/거래 잠금, 현재 개체 버전·배치 상태를 확인합니다. 판매 중 색 수정·배치 변경 허용 여부는 상태 규칙으로 정하고, 동시 요청이 이 규칙을 우회하지 못하게 합니다.
- **검사와 변경은 하나의 DB 트랜잭션으로 처리합니다.** 구매 시 현재 판매 상태·소유자·가격·잔액을 확인하고, 재화 차감·지급·소유권 이전·판매 종료를 함께 확정합니다. 개체·잔액에 대한 동시 갱신을 잠금 또는 조건부 갱신으로 제어하고, DB 제약으로 중복 소유·중복 지급·음수 잔액을 방지합니다. 배치도 같은 개체의 거래와 경합할 수 있으므로 같은 규칙을 적용합니다.
- **재전송과 중복 처리를 구분합니다.** 계정·행위·요청 ID에 처리 결과를 연결하며 같은 ID로 내용을 바꾸면 거부합니다. 새 요청 ID를 계속 보내도 같은 도전 보상이나 같은 물건의 판매가 반복 확정되지 않도록 업무 단위의 유일성도 검사합니다.
- **오래된 클라이언트 상태로 권한을 복구하지 않습니다.** 양도와 충돌하는 서버 배치는 함께 해제하거나 거래를 거부하는 일관된 규칙을 둡니다. 접속·복귀·재연결 시 서버 기록으로 동기화합니다. 매 프레임 DB 조회는 필요하지 않지만, 민감한 변경을 오래된 클라이언트 캐시만으로 승인하지 않습니다. 연결 실패 시 실제 거래·보상·생성을 로컬에서 확정하지 않습니다.
- **파일 접근과 소유권은 별도 권한입니다.** 원본은 비공개 저장소에 보관하고, 접근이 허용된 요청에만 전달합니다. 타인의 마을 방문·상점 미리보기의 표시 권한은 명시적으로 설계하며, 표시 권한을 수정·배치·재판매 권한으로 확대하지 않습니다. 기본 클라이언트 경로는 생성 GLB를 평문 파일로 저장하지 않고 메모리에서 로드하는 방식입니다. 현재 배포용이 아닌 자체 테스트 샘플 GLB는 이에 해당하지 않습니다.
- **전달된 데이터의 회수는 보장하지 않습니다.** 메모리 로드와 암호화 캐시도 모델 추출을 완전히 막지 못합니다. 짧은 만료 URL 역시 유효 기간 중 재사용될 수 있고 다운로드된 데이터를 삭제하지 못합니다. 즉시 권한 철회가 필요한 파일 요청은 서버 중계 등 요구 수준에 맞는 방법을 선택합니다. 모델 복사를 공식 소유권·재화 복제로 연결하지 않는 것이 서버의 보호 범위입니다.
- **실제 비용이 드는 보상과 생성은 별도 검증을 거칩니다.** 클라이언트의 클리어 신고·이벤트 기록만으로 정당한 플레이를 증명할 수 없습니다. 서버가 판정하는 생존 규칙 또는 검증 가능한 도전 프로토콜을 구현하기 전에는 로컬 점수로 실제 생성권을 지급하지 않습니다. 계정별·서버 전체 사용 상한도 적용합니다. 공급자 요청 후 응답이 유실되면 상태를 먼저 확인하며 유료 생성을 무조건 재시도하지 않습니다.
- **운영 기록과 세션 보호를 포함합니다.** 인증 세션 만료·폐기와 요청 제한을 적용하고, 승인·거부·거래 전후 상태·재화 원장·요청 ID를 추적 가능한 형태로 기록합니다. API 키·인증 토큰·모델 접근용 비밀 URL은 로그에 남기지 않습니다.

### 서버 완료 판정에 필요한 검증

다음은 향후 구현할 통합 테스트 목록입니다. 현재 `game/tests/smoke.gd`는 로컬 게임 검사이며 아래 보안 검사를 대체하지 않습니다.

| 파일 복사·옛 세이브 복원·타인 미리보기 데이터 사용 | 공식 소유 개체·배치 권한·재화·재판매 권한이 생기지 않음 |
| 조작한 생존 결과·음수 금액·변조 가격·생성 한도 초과 | 서버가 거부하며 실제 API 예산을 추가 소비하지 않음 |

설계 참고: [OWASP 권한 검증](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP 거래 권한 검증](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html), [PostgreSQL 동시 접근 제어](https://www.postgresql.org/docs/current/explicit-locking.html). DB 제품과 호스팅은 아직 선택하지 않았습니다.

인계된 계정 진단은 401 이후 HTML 400을 받은 상태이며, 마지막 Tkinter 코드의 후속 결과가 없습니다. 계정·잔액·대회 크레딧 지급 여부는 아직 확인하지 않았습니다. API 키를 자료나 로그에 출력하지 않습니다.

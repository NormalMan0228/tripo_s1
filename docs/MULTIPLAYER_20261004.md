# 3인 멀티플레이 테스트 — 2026-10-04

> **2026-10-05 저녁 갱신:** 잠시 보류했던 멀티플레이를 다시 켰다. 서버가 `multiplayer_protocol: 1`을 알리면 마을 HUD 왼쪽(캐릭터 프레임 아래)에 `함께하기`·`인사` 버튼이 나온다. 혼자 하려면 `--no-multiplayer` 인자로 끈다. 메인 마을이 다섯 섬 지도로 바뀐 뒤의 검증 결과는 아래 "섬 마을 재검증" 절에 있다.

## 상태

개인 마을 방문과 2~3인 협동 생존을 구현하고 로컬에서 검증했다. Windows 테스트 실행본은 `builds/Tripothon_Multiplayer_Test/Tripothon.exe`다. 같은 폴더의 `Tripothon.pck`가 필요하다.

**2026-10-05 갱신: 온라인 서버에 멀티플레이 버전이 반영되어 있다.** `https://34-28-65-113.sslip.io/health`가 `mode=live`, `protocol=6`, `multiplayer_protocol: 1`, `max_party_members: 3`을 반환하는 것을 읽기 전용으로 확인했다. 게임은 이 두 값을 보고 함께하기를 켠다. 버전 문자열은 여전히 `0.8.1`이라 이 값만으로 멀티플레이 반영 여부를 판단하면 안 된다. 테스트 빌드(10/4 17:53)와 그 뒤의 서버 소스 ZIP·현재 `server/multiplayer.py`는 내용이 같다.

배포 시각·수행자·배포 전 백업·기존 계정 보존 여부는 이 저장소에 기록이 없다. 아래 [온라인 반영 기록](#온라인-반영-기록)에 확인되는 대로 채운다. 서로 다른 PC에서 실제로 접속하는 온라인 검증은 아직 수행하지 않았다.

## 테스트 순서

1. 같은 HTTPS 서버 주소를 사용하는 새 테스트 실행본을 세 PC에 전달한다. 서버의 기존 가입 초대 코드는 운영자가 별도로 전달하며 배포 ZIP에는 넣지 않는다.
2. 서로 다른 사용자 이름으로 가입·로그인한다. 각 계정의 마을·가구·재화·생활 저장은 분리된다.
3. 화면 위 `함께하기 · 초대 / 파티`에서 상대의 정확한 사용자 이름을 입력하고 `내 마을로 초대`를 누른다. 상대가 같은 메뉴에서 수락한다.
4. 주인을 포함해 최대 3명이 같은 마을을 산책한다. 서로의 이름·위치·외형과 주인이 배치한 야외 가구·텃밭을 볼 수 있다. 인사와 텍스트 대화를 보낸다.
5. 방문자는 `내 마을로 돌아가기`, 주인은 `방문 종료`를 사용할 수 있다. 방문자에게 가구·텃밭 편집 권한은 주지 않는다. 이번 버전에서 함께 방문하는 공간은 야외 마을이며 집·공방 실내 방문은 지원하지 않는다.
6. 한 명이 `파티 만들기`를 누르고 두 명을 `파티로 초대`한다. 모두 수락하고 마을 화면에 접속해 있어야 한다. 개인 생존 탐험이 진행 중이면 먼저 마친다.
7. 파티장이 지역·난이도를 선택하고 `파티 함께 출발`을 누른다. 파티원도 자동으로 같은 생존 맵에 들어간다. 처음에는 `산책` 난이도를 사용한다.
8. 한 명이 채집했을 때 다른 화면에서도 자원이 줄어드는지, 모닥불과 적이 공유되는지, 각자의 가방·체력이 구분되는지 확인한다.
9. 한 명이 Esc 메뉴를 열어도 다른 사람의 생존은 계속된다. `귀환`하면 그 사람만 탐험에서 빠지고 완주 보상을 포기한다. 게임 창만 닫았다가 다시 로그인하면 같은 협동 탐험으로 복귀한다.
10. 7일 생존 보상은 중도 포기하지 않은 참여자에게 각각 한 번 지급한다. 종료 직후 연결이 끊겨도 `함께하기`의 미수령 협동 보상으로 받는다. 이야깃길 첫 완료 보너스는 이번 협동 버전에서 적용하지 않는다.

## 서버 규칙

| 항목 | 규칙 |
|---|---|
| 마을 정원 | 주인 자리 1 + 방문 허가 2 |
| 방문 초대 | 대상 계정만 수락, 10분 만료 |
| 방문 허가 | 수락 후 1시간, 주인이 종료 가능 |
| 파티 | 2~3명 출발, 파티장 이탈 시 남은 멤버에게 파티장 이전 |
| 생존 상태 | 하나의 시간·맵·자원·적·모닥불, 개인 체력·허기·기력·가방 |
| 입력 | 클라이언트는 이동 의도·행동·증가하는 순번만 제출 |
| 이동 입력 만료 | 0.6초 동안 새 입력이 없으면 이동 중지 |
| 접속 표시 | 10초 동안 새 활동이 없으면 연결 끊김으로 표시 |
| 중도 연결 끊김 | 동료가 활동하면 세계는 계속됨. 남은 캐릭터는 위험에 노출됨 |
| 전원 연결 끊김 | 오프라인 시간을 소급 적용하지 않고 저장 상태에서 재개 |
| 사망 | 관전, 동료가 모두 쓰러지면 실패 |

| 통신 | 기존 HTTPS/HTTP 요청. 마을 위치 약 4Hz, 협동 입력 최대 5Hz, 생존 중 소셜 갱신 약 2초 |

마을의 이동·높이 보고는 외형 표시용이며 경제적 권한을 부여하지 않는다. 협동 생존의 이동·시간·행동은 서버가 계산한다. 이번 전송 방식은 작은 그룹의 시험용이며 지연 보정·예측 이동·WebSocket 전송·공유 실내·아이템 전달·부활은 후속 범위다.

## 구현

- `server/multiplayer.py`: 대상별 초대, 방문 권한, 접속 정보, 대화, 파티, 협동 API, 방문객용 읽기 전용 모델 경로.
- `server/coop.py`: 공유 세계를 한 번만 진행하고 개인 이동·생존 규칙을 적용한다. 동일 시각에 세 명이 요청해도 시간이 세 배로 증가하지 않는다.
- `server/database.py`: 쓰기 예약 없이 사용하는 읽기 연결. 새 멀티플레이 테이블은 기존 데이터베이스에 추가한다.
- `server/app.py`: 기능 협상, 계정별 일반 API 제한, 로그인 해시 검증을 DB 쓰기 잠금 밖으로 이동, 읽기 경로 개선.
- `game/scripts/social.gd`: 초대·파티·대화 화면, 방문 모델 표시, 동료 보간, 자동 파티 입장.
- `game/scripts/main.gd`: 기존 생존 UI를 협동 상태에도 사용. 멀티 메뉴를 열어도 서버 입력을 계속 보낸다.

협동 서버는 기존과 같이 **단일 Uvicorn 프로세스**로 실행한다. AI 공급자·과금 설정은 변경하지 않았다.

## 2인 PC방 검증 — 계획 (2026-10-05)

3인·서로 다른 집 검증 전에 PC방 두 자리에서 2인 온라인 검증을 먼저 한다. 2인은 마을 방문(주인+방문자 1)과 협동 생존(최소 2명) 모두 지원한다.

### 준비

- 실행본: `artifacts/Tripothon_Multiplayer_Windows_20261004.zip`(약 137MB). 압축을 푼 뒤 `Tripothon.exe`와 `Tripothon.pck`가 같은 폴더에 있어야 한다. 클라우드 드라이브·USB 등으로 가져간다. PC방 PC는 재부팅하면 파일이 지워지는 경우가 많으므로 테스트 도중 재부팅하지 않는다.
- 서명되지 않은 실행 파일이라 Windows SmartScreen 경고가 나올 수 있다. `추가 정보 → 실행`으로 진행한다. PC방 관리 프로그램이 외부 EXE 실행을 막으면 그 자리에서는 검증할 수 없다.
- 계정: 기존 온라인 계정 2개 또는 신규 가입 2개. 신규 가입에는 서버 운영자의 초대 코드(서버 비밀값, 모든 가입자 공용)가 필요하다. 초대 코드는 ZIP·문서·채팅 기록에 남기지 않는다. PC방 PC의 로그인 정보는 테스트 후 로그아웃한다.
- 이 빌드는 플레이어용이라 F3 개발 정보가 없다. 지연은 체감과 화면 녹화로 기록한다.

### 이 검증의 한계

- 두 PC가 같은 PC방 공인 IP를 공유한다. 인증 API 제한(IP당 20회/60초)도 두 사람이 나눠 쓴다. 정상 플레이에서는 닿지 않지만, 로그인을 반복하다 `rate_limited`가 나오면 1분 기다린다.
- **서로 다른 네트워크·3인 정원 검증은 대신하지 못한다.** 마스터 계획의 "병행 A" 완료 판정은 3인·다른 집 검증 후에 한다.
- 서버는 미국 중부 e2-micro다. 한국에서의 지연은 로컬 부하 시험(p95 73ms)보다 크다.

## 온라인 반영 절차 (참고: 10/4 작성)

아래는 10/4에 원격 관리 세션 없이 작성한 반영 절차다. 이후 서버가 반영된 것은 확인했지만, 이 절차를 그대로 따랐는지는 기록이 없다. 다음 서버 갱신 때도 같은 절차를 따른다. 서버 소스 ZIP(`artifacts/Tripothon_Multiplayer_Server_20261004.zip`)에는 계정 DB, 키, 초대 코드, 개인 생성물이 없다.

1. 기존 VM의 저장소 위치·Compose 프로젝트·볼륨 이름을 확인한다. 실행 중인 컨테이너의 설정과 비밀 파일을 보존한다.
2. 기존 운영 절차대로 `/data`의 DB와 자산을 함께 백업하고 검증한다.
3. 서버 소스 변경을 기존 체크아웃에 반영한다. `ops/production.env`, `ops/secrets`, Docker 볼륨을 덮어쓰거나 삭제하지 않는다.
4. 기존과 동일한 Compose 프로젝트/파일 인자로 API 이미지만 빌드·갱신한다. 예시: `docker compose --env-file ops/production.env -f ops/compose.yaml -f ops/compose.gcp-free.yaml up -d --build api`. 기존 배포가 다른 인자를 사용하면 그 인자를 유지한다.
5. HTTPS `/health`의 `multiplayer_protocol: 1`을 확인하고 기존 계정·재화·물건이 남아 있는지 확인한다.
6. 세 집의 PC로 위 테스트 순서를 수행한다. 우선 15분 이상 플레이하면서 입력 지연, 접속 복원, 오류, CPU·메모리를 기록한다. 온라인 3인 용량은 이 검사 후 판단한다.

서버 실행 정보와 비밀·백업 절차는 [운영 문서](../ops/README.md)를 따른다.
